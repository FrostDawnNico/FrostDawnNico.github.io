C++ Memory Management

Posted on 2026-05-10 Edited on 2026-05-16

深入探讨C++的内存管理机制，包括智能指针、RAII以及内存泄漏检测等核心概念。

内存管理

基本概念

  1. 内存分区

内存运行时，内存的5个分区：栈区 堆区 全局/静态区 常量区 代码区

  1. 堆内存操作核心：new/delete

new操作符：在堆上分配内存，并返回指向该内存的指针。

delete操作符：释放内存。

注意：new和delete必须成对使用，否则会导致内存泄漏。

  1. 内存泄漏

问题：程序申请的内存在使用完毕后未释放。

后果：长期的内存泄漏会导致系统内存资源不足，影响程序性能甚至导致程序崩溃

  1. 野指针

问题：指针指向的内存已释放，但指针没置空，还在使用

后果：使用野指针会导致未定义的行为，可能引发程序崩溃或数据损坏。

  1. 重复释放内存

问题：同一块内存释放两次

后果：程序崩溃

内存区域划分

内存区域 存储内容 生命周期 管理方式 特点
栈区 (Stack) 局部变量、函数参数 函数执行自动创建，结束自动释放 系统自动管理 栈区内存管理效率高，但空间有限，且分配的内存大小在编译时确定。
堆区 (Heap) 动态分配的内存（new） 手动申请，手动释放 new/delete 堆区空间大，但分配和释放效率低于栈区，若管理不善易导致内存泄漏。
全局/静态区 全局变量和静态变量 程序启动创建，结束销毁 系统自动管理 该区域变量在整个程序运行期间都存在。
常量区 字符串常量和const全局变量 程序全程存在，只读 系统自动管理 常量区的内容在程序运行期间不可修改。
代码区 程序的二进制代码，即函数的机器指令 程序全程存在 系统自动管理 代码区通常是只读的，防止程序意外修改自身代码。
重点：我们说的内存管理，99% 都是指堆区内存的手动申请和释放。

堆内存核心操作：new /delete

new操作符:C++ 用 new 申请堆内存，返回指向该内存的指针。

delete操作符:delete 释放 new 申请的内存，两者必须成对使用。

内存对齐:new 分配内存时会考虑内存对齐，提高访问效率。

内存分配失败:new 可能因内存不足分配失败，返回 nullptr。

关键规则：

new 和 delete 必须成对使用，只申请不释放 = 内存泄漏

数组必须用 delete[]，用普通 delete 会导致内存泄漏

内存释放后，指针必须置空 nullptr，否则变成野指针

示例代码：

// 1. 定义+初始化
int* p = nullptr;

// 2. 申请堆内存
p = new int(66);

// 3. 使用前判空（防御性编程）
if (p != nullptr)
{
    cout << *p << endl;
}

// 4. 释放 + 立刻置空（关键！）
delete p;
p = nullptr;

C 语言风格：malloc /free

malloc/free函数：C++ 兼容 C 的内存函数，但不推荐使用malloc在堆上分配内存

#include <cstdlib>

// 申请4字节int内存
int* p = (int*)malloc(sizeof(int));

// 释放
free(p);
p = nullptr;

new/delete对比 malloc/free

malloc/free：C 语言的库函数，只负责分配 / 释放裸内存，不处理对象。
new/delete：C++ 的关键字 / 运算符，会分配内存 + 调用构造 / 析构函数，专门用于对象。

维度 new/delete malloc/free
属性 运算符（可被重载） 库函数（不可重载）
构造/析构 自动调用构造函数和析构函数 不调用任何构造/析构函数
返回类型 返回具体类型指针（类型安全） 返回 void*（需强制转换）
失败处理 抛出 std::bad_alloc异常 返回 NULL（需手动检查）
内存分配 计算所需大小（无需手动算） 需显式指定字节数（sizeof）
底层关系 通常底层调用 malloc实现 纯粹的堆内存分配

深度解析与底层原理

  1. 对象生命周期的管理（最重要、最本质的区别）

malloc：仅仅是从堆上挖一块内存给你，这块内存里可能是“垃圾”数据，C++ 不会帮你初始化对象。

new：做两件事：

· 调用 operator new分配内存（底层通常是 malloc）。

· 在分配的内存上调用构造函数，初始化对象。

  1. 数组的处理

new[]/ delete[]：会调用数组中每一个元素的构造函数/析构函数。

malloc：只分配一块连续内存。

致命陷阱：用 malloc分配的对象数组，如果用 delete[]释放，行为是未定义的；反之亦然。

  1. 内存不足时的行为

new：默认抛出 std::bad_alloc异常。如果使用 new (nothrow) Object()，则返回空指针。

malloc：返回 NULL。

追问与陷阱

❓ new和 delete是如何实现的？

new的实现逻辑：

调用 operator new(size_t size)（可以重载）。

调用构造函数。

delete的实现逻辑：

调用析构函数。

调用 operator delete(void* ptr)。

❓ 为什么 malloc分配的内存不能用 delete释放？

未定义行为（UB）。因为 delete会试图调用析构函数，并可能调用 free之外的内存回收逻辑。混合使用会导致堆损坏（Heap Corruption）。

❓ Placement new（定位 new）是什么？

它允许你在已分配的内存上构造对象，而不重新分配内存。

char buffer[sizeof(Object)]; // 栈上预分配内存
Object* obj = new (buffer) Object(); // 在 buffer 上构造
obj->~Object(); // 必须手动调用析构函数，不能 delete

用途：内存池、嵌入式开发，用于精确控制对象构造位置。

补充

现代 C++ 的态度：

  1. 避免使用裸指针：在现代 C++ 中，直接使用 new/delete被认为是危险的（容易忘 delete或导致异常安全问题）。

  2. 使用智能指针：std::unique_ptr和 std::shared_ptr封装了 new，自动管理 delete，是最佳实践。

  3. 使用 std::allocator：如果需要自定义内存管理，标准库提供了更安全的 std::allocator，而不是直接重载 operator new。

总结：malloc/free是 C 的遗产，只负责内存；new/delete是 C++ 的，负责对象生命。但在现代 C++ 中，我们应该尽量避免手动使用它们，转而使用 RAII和 智能指针来确保内存安全。

内存泄漏

void fun()
{
    int* p=new int(10);//直接返回未释放，没有delete p，内存泄漏
}

解决方案：使用智能指针（如std::unique_ptr）自动管理内存，避免手动释放的麻烦。

void func()
{
    // 使用智能指针    
    std::unique_ptr<int> ptr(new int(10)); 
    if (some_condition) 
    { 
        return; // 智能指针自动释放内存  
    }   
    // 无需手动释放
}

野指针

野指针是C++中常见且危险的问题，需谨慎处理

产生原因： 指针变量未初始化，或指向的内存被释放后未置空、指针越界指向已销毁栈对象。

危害： 使用野指针会导致未定义行为，可能引发程序崩溃或数据损坏。

示例代码

int* p = new int(10);
delete p;// p 现在是野指针！
cout << *p << endl;  // 非法访问，崩溃

解决方案：

指针定义即初始化，默认给 nullptr

delete 后立刻赋值 nullptr

使用指针前先判空 if (ptr != nullptr)

// ❌ 错误：未初始化，随机地址 → 野指针
int* p;

// ✅ 标准写法：初始化为空指针
// 1. 定义+初始化
int* p = nullptr;    
// 2. 申请堆内存
p = new int(66);    
// 3. 使用前判空（防御性编程）
if (p != nullptr) {
    cout << *p << endl;
}
// 4. 释放 + 立刻置空
delete p;
p = nullptr;

杜绝：指向局部栈变量的指针外流（栈野指针）

// ❌ 严重错误：返回局部变量地址
int* getAddr()
{
    int a = 10;
    return &a;
}
// 函数结束 a 销毁，返回的是野指针

动态数组标准安全写法：

int* arr = nullptr;
arr = new int[10];

// 使用
arr[0] = 1;

// 数组必须 delete[] + 置空
delete[] arr;
arr = nullptr;

重复释放内存

重复释放内存是一种严重的内存管理错误，会导致程序行为不可预测。

问题表现： 对同一块内存多次调用delete，通常发生在代码逻辑复杂或异常处理不当时。

危害： 重复释放内存会破坏内存管理系统的数据结构，可能导致程序崩溃、数据损坏或安全漏洞。

示例代码

int* p = new int(10);
delete p;
delete p;  // 错误！重复释放

解决方案

使用智能指针避免手动管理内存，

在释放内存后显式将指针置为nullptr，防止重复释放。

智能指针概述

设计初衷与核心思想

场景需求

当程序手动申请资源后抛出异常，会导致资源未释放而造成内存泄漏。智能指针能自动管理资源，避免此类问题。

RAII思想

RAII即资源获取即初始化，它利用对象的生命周期来管理资源。在对象构造时获取资源，在析构时释放资源，确保资源的正确释放。

设计思路

智能指针类封装了原始指针，在其析构函数中自动释放所管理的资源。同时重载了*、->等运算符，方便对资源的访问。

运算符重载

通过重载operator*、operator->和operator[]等，使智能指针对象能像普通指针一样被使用，保证了代码的兼容性和易用性。

unique_ptr详解

独占式智能指针的特性和用法

  1. 独占所有权

unique_ptr独占其所指向对象的内存，任何时刻都只有一个

unique_ptr拥有该对象的所有权，确保了资源的独占性。

  1. 禁止拷贝

unique_ptr禁止通过拷贝构造函数和赋值运算符进行拷贝，这从根本上防止了多个智能指针同时管理同一块内存，避免了资源释放的混乱。

  1. 支持移动

虽然禁止拷贝，但unique_ptr支持通过std::move进行移动语义。所有权可以通过移动操作从一个unique_ptr转移到另一个，原unique_ptr将不再拥有资源。

  1. 自定义删除器

unique_ptr允许用户指定自定义的删除器，以适应不同的资源释放需求，例如释放数组内存或调用特定的释放函数。

shared_ptr详解

共享式智能指针的特性和用法

  1. 共享所有权

多个shared_ptr可以共同管理同一个对象，通过引用计数机制来追踪有多少个shared_ptr共享该资源。

  1. 引用计数

shared_ptr内部维护一个引用计数，每当有新的shared_ptr指向该对象时，计数加一；当一个shared_ptr被销毁或重置时，计数减一。当计数为零时，说明没有shared_ptr再指向该对象，此时会自动释放资源。

  1. 线程安全

shared_ptr的引用计数操作是原子的，因此多个线程可以安全地拷贝或销毁不同的shared_ptr实例。但其所指向的对象本身的访问仍需额外的同步机制。

  1. 循环引用问题

当两个或多个shared_ptr相互引用时，会形成循环引用，导致它们的引用计数永远不为零，从而造成内存泄漏。可以使用weak_ptr来打破循环引用。

weak_ptr解决循环引用

弱引用指针如何打破共享指针的循环依赖

  1. 循环引用场景

当shared_ptr<A>包含一个shared_ptr<B>，而shared_ptr<B>又包含一个shared_ptr<A>时，形成循环，引用计数无法降为零。

  1. weak_ptr特性

weak_ptr是一种弱引用，它不增加对象的引用计数。它指向一个由shared_ptr管理的对象，但不拥有该对象。

  1. 解决方案

将循环引用中的一方改为weak_ptr，可以打破循环。例如，B类中保存A类的weak_ptr，这样A的析构就不会被B的shared_ptr引用所阻碍。

  1. 使用注意事项

weak_ptr必须通过lock()方法转换为shared_ptr后才能安全访问对象，以防止对象已被释放。

内存泄漏检测

如何定位和解决内存泄漏问题

问题： 程序中手动new的对象，若在抛出异常后未执行对应的delete语句，就会导致内存泄漏。这种情况在代码逻辑复杂或异常处理不当时尤为常见。

传统解决方法： 在try-catch块中进行资源的申请和释放。在catch块中捕获异常后，先手动释放已申请的资源，然后再将异常重新抛出。但这种方法代码冗余，且难以处理多重资源申请的复杂情况。

智能指针优势： 使用智能指针可以彻底避免手动管理资源的繁琐和风险。智能指针作为局部对象，其析构函数会在离开作用域时自动被调用，从而确保资源被及时释放，无需关心异常是否发生。

RAII机制核心

C++资源管理的核心设计模式

核心思想：
RAII全称Resource Acquisition Is Initialization，即资源获取即初始化。它将资源的生命周期绑定到对象的生命周期上。

实现原理 ：
在对象的构造函数中申请资源，在析构函数中释放资源。利用C++的栈展开机制，即使发生异常，局部对象的析构函数也会被自动调用，从而保证资源的释放。

应用场景 ：
RAII不仅用于内存管理（如智能指针），还广泛应用于文件句柄、互斥锁、网络连接等任何需要手动释放的资源管理场景。

优势总结：
RAII将资源管理的复杂性封装在对象内部，使代码更简洁、异常安全，并有效防止资源泄漏。

常见考题

C++内存是什么

C++ 程序运行时在操作系统中占据的虚拟地址空间布局。

分区 英文名 存储内容 生命周期 管理方式
栈 (Stack) Stack 局部变量、函数参数、返回地址 随函数调用/返回自动创建/销毁 编译器自动管理
堆 (Heap) Heap 动态分配的内存 (new/malloc) 手动分配，手动释放 程序员手动控制
全局/静态区 Data/BSS 全局变量、静态变量 (static) 程序启动时分配，结束时释放 操作系统管理
常量区 Text/ROData 字符串字面量、const常量 程序整个运行期间存在 只读，不可修改
代码区 Text Segment 程序的机器指令（二进制代码） 程序整个运行期间存在 只读，防止被篡改
  1. 栈（Stack）：高速但有限

特点：内存分配连续，速度极快（仅移动栈顶指针）。

面试陷阱：

栈溢出（Stack Overflow）：通常由无限递归或定义过大的局部数组（如 int arr[10000000]）引起。

返回局部变量地址：函数返回后，栈帧被回收，指针变成悬空指针。

  1. 堆（Heap / Free Store）：灵活但危险

特点：内存不连续，空间大（受限于虚拟内存），分配速度慢，容易产生碎片。

C++ 特有：C++ 中的 new分配的区域通常称为 自由存储区 (Free Store)，理论上可以通过重载 operator new改变其来源（不一定非得是堆），但在绝大多数实现中等同于堆。

核心考点：内存泄漏（忘了 delete）和 二次释放（对同一指针 delete两次）。

  1. 全局/静态区（Data Segment）

.data 段：存放已初始化的全局变量和静态变量。

.bss 段：存放未初始化的全局变量（会被自动清零）。

代码示例：

#include <iostream>
using namespace std;

int g_var = 10;        // 全局区 (.data)
static int s_var;      // 全局区 (.bss，自动初始化为0)
const char* str = "Hi";// str 在全局区，"Hi" 在常量区

void func() {
int local = 20;          // 栈区
int* heap_var = new int; // heap_var 指针在栈区，*heap_var 在堆区
*heap_var = 30;
delete heap_var;
}

int main() {
func();
return 0; // 代码区存储 main 和 func 的指令
}

高频追问

❓栈和堆的主要区别？

对比项 栈 (Stack) 堆 (Heap)
分配效率 极高（仅寄存器移动） 较低（需遍历空闲链表）
空间大小 较小（通常几 MB） 很大（接近虚拟内存上限）
碎片 无（先进后出） 有（频繁分配释放产生外部碎片）
分配方式 连续内存 不连续内存

❓char* p = "Hello";存储在哪？

Hello存储在 常量区（只读）。

p是一个指针，存储在 栈区（如果是局部变量）或 全局区。

危险操作：p[0] = 'h';会导致段错误（Segmentation Fault），因为试图修改只读内存。

正确解决方案：

方案一：字符数组（最常用，栈分配）

将字符串复制到栈上的数组，数组位于栈区（可读写）。

char p[] = "Hello"; // 在栈上创建副本
p[0] = 'h';         // 正确：修改栈上的数据
// 输出: "hello"

方案二：std::string（现代 C++ 首选）

使用标准库容器，内部管理动态内存，安全且功能丰富。

#include <string>
std::string s = "Hello";
s[0] = 'h'; // 正确：std::string 支持修改
// 输出: "hello"

方案三：动态分配（需手动管理内存，不推荐）

使用 new[]在堆上分配内存（记得释放，否则内存泄漏）。

char* p = new char[6];
strcpy(p, "Hello");
p[0] = 'h'; // 正确：修改堆上的数据
delete[] p; // 必须手动释放

方案对比：

方案 内存区域 安全性 推荐度 评价
字符数组 栈 (Stack) 高（自动回收） ⭐⭐⭐⭐ 体现对栈内存的理解。
std::string 堆 (Heap) 最高（RAII） ⭐⭐⭐⭐⭐ 体现现代 C++ 工程素养。
动态分配 堆 (Heap) 低（易泄漏） ⭐ 除非明确要求手动管理内存。
追问：

Q: 如何安全地获取字符串首地址？

A：使用 std::string。

std::string s = "Hello";
char* p = &s[0]; // 或 s.data()
p[0] = 'h';      // 安全

注意：C++11 起 std::string保证连续存储，可以直接当 char*使用，但需确保字符串未因扩容导致指针失效。

补充 （可跳过）：要确保 std::string的指针（如 &s[0]或 s.data()）不因扩容而失效，核心原则是：在持有指针期间，禁止任何可能导致重新分配内存的操作。

  1. 预先预留空间（最推荐）

在获取指针之前，使用 reserve()强制分配足够大的容量。只要后续操作不超出这个容量，就不会发生重新分配（扩容）。

#include <string>

std::string s;
s.reserve(100); // 预先申请 100 个字符的空间

char* p = &s[0]; // 获取指针
// 只要 s.size() 不超过 100，p 就一直有效
s.append("Hello"); // 安全：size=5，未超过 capacity=100
s.append(95, '!'); // 安全：size=100，刚好满
// s.push_back('?'); // 危险：此时 size=101 > capacity=100，会扩容，p 失效
  1. 使用 std::string_view（现代 C++ 最佳实践）

如果你只是需要“查看”或“传递”字符串内容，而不需要修改，使用 std::string_view。它不拥有内存，只是一个视图，因此完全避免了扩容问题（但要注意原始字符串的生命周期）。

#include <string>
#include <string_view>

std::string s = "Hello";
std::string_view sv = s; // 不拷贝，只是视图

// 只要 s 不被销毁或修改导致扩容，sv 就是安全的
// 注意：如果 s 扩容，sv 可能悬空
  1. 使用 std::vector<char>（替代 std::string作为缓冲区）

如果你需要一个可修改的、连续的字符缓冲区，且担心 std::string的 COW（写时拷贝）或扩容问题，std::vector更安全。

std::vector<char> buffer(100); // 预分配，永不失效
char* p = buffer.data();

// 填充数据
snprintf(p, buffer.size(), "Hello %d", 123);

// 如果需要转为 string
std::string s(p);

语义明确（这就是个缓冲区），扩容行为比 std::string更容易预测。

  1. 使用 c_str()的瞬时性（C 接口交互）

当需要传递给 C API 时，通常要求 const char*。永远不要长期存储 c_str()返回的指针。

总结：永远不要长期持有 std::string的内部指针。

如果需要修改，用 std::string对象本身操作。缓冲区用 std::vector：替代 char*数组管理。

如果需要传递，用 std::string_view（只读）替代所有 const char*参数，或重新获取指针（确保生命周期内未扩容）。

如果必须存指针，使用 reserve()锁定容量。

Q: const char* p = “Hello”;

A: 加上 const是编译器层面的保护，这是“只读”的正确声明方式。

❓内存对齐（Memory Alignment）是什么？(C++基础中有详细内容)

概念：数据在内存中的起始地址必须是其大小的整数倍（如 int通常在 4 的倍数地址上）。

原因：CPU 读取对齐的数据效率更高；某些硬件架构不对齐会直接崩溃。

影响：sizeof(Class)的结果通常大于成员变量大小之和，因为有填充字节（Padding）。

补充：现代 C++ 的内存观

RAII：资源获取即初始化，利用栈对象的确定性析构来管理堆资源。

智能指针：std::unique_ptr和 std::shared_ptr是解决堆内存泄漏的标准方案。

内存池：在高性能场景下，为了避开频繁的 new/delete开销和碎片，会使用内存池预先申请大块内存。

总结： C++ 内存管理的核心在于明确对象存活的位置（栈还是堆）。记住：能用栈就用栈，必须用堆时用智能指针。

指针、指针声明和引用

基本概念

  1. 指针（Pointer）是一个变量，它存储的是另一个变量的内存地址。

    int a = 10;
    int* p = &a;
    //p：指针变量；✅ 指针本身占用内存（通常 4 / 8 字节）
    //&a：变量 a的地址；
    //*p：解引用，访问指针指向的值

✅ 指针的大小通常相同

sizeof(int*) == sizeof(char*) // 通常相同

✅ 指针的四种状态

空指针： int* p = nullptr;

野指针： 未初始化

悬空指针： 指向已释放内存

有效指针： 指向合法对象

⚠️使用指针前一定要判空，避免野指针。

  1. 指针声明

关键修饰符与陷阱：const与指针的组合

const修饰左边的内容（如果左边没东西，就修饰右边）。 const修饰左边的内容（如果左边没东西，就修饰右边）。

声明 名称 特性
const int* p 指向常量的指针 指针可变，值不可变。
int* const p 常量指针 指针不可变，值可变。
const int* const p 指向常量的常量指针 都不可变。

复杂声明解析：

遵循 右左法则 (Right-Left Rule)： 从标识符开始，先向右看，再向左看，遇到括号就跳进去。

声明 读法 含义
int* p[10]; 指针数组 包含 10 个 int* 元素的数组。
int (*p)[10]; 数组指针 指向“包含 10 个 int 的数组”的指针。
int* func(); 指针函数 返回 int* 的函数。
int (*func)(); 函数指针 指向返回 int 的函数的指针。
int (*p[10])(); 函数指针数组 包含 10 个“指向返回 int 的函数”的指针的数组。 
// 定义一个函数，接受 int 返回 int
int add(int a) { return a + 1; }

// 声明一个函数指针并赋值
int (*func_ptr)(int) = &add;
// 也可以直接写成int (*func_ptr)(int) = add;
// 这两种写法都是正确的，并且效果相同。&运算符在这里是可选的，因为函数名本身就可以隐式地转换为函数的地址

// 通过指针调用函数
int result = func_ptr(5); // result = 6

  1. 引用（Reference）是某个变量的别名，不单独占内存。

    int a = 10;
    int& r = a; //操作 r等价于操作 a

三大特性: ✅ 必须初始化✅ 不能重新绑定✅ 本质通常是常量指针（编译器实现）
int& r ↔ int* const r

指针 vs 引用

重点在于是否可为空和是否可重定向

维度 指针 (Pointer) 引用 (Reference)
本质 一个存储内存地址的变量。 一个已存在变量的别名。
空值 (Null) 可以为 nullptr。 不可以为空（必须初始化）。
重定向 可以改变指向的对象。 不可以改变绑定的对象（从一而终）。
内存 有自己的内存地址（栈上），存储目标地址。 通常（但不总是）通过指针实现，逻辑上不占新内存。
安全性 低（野指针、空指针解引用风险）。 高（引用必须绑定有效对象）。

能用引用就不要用指针，除非需要表示“无对象”或动态内存。

常见代码

✅ 交换函数

// 值传递 ❌
void swap(int a, int b);
// 指针传递 ✅
void swap(int* a, int* b) {
    int t = *a;
    *a = *b;
    *b = t;
}
// 引用传递 ✅✅
void swap(int& a, int& b) {
    int t = a;
    a = b;
    b = t;
}

❌ 指针作为返回值（危险）

int* func() {
    int x = 10;
    return &x; // ❌ 返回局部变量地址，悬垂指针
}

根本原因：局部变量在栈上分配，函数结束即销毁，返回的地址指向一块 已经不属于你的内存

❌ 返回局部变量（陷阱）

int& func() {
    int x = 10;
    return x; // ❌ 返回局部变量，悬垂引用
}

正确做法：

✅ 方案 1：返回普通值（最推荐）

int func() {
    int x = 10;
    return x;  // 返回拷贝
}

✅方案 2：使用静态变量（慎用）

int* func() {
    static int x = 10;
    return &x;
}

⚠️ 缺点：非线程安全；多次调用共享同一变量

✅ 方案 3：使用动态内存（需手动释放）

int* func() {
    int* x = new int(10);
    return x;
}

⚠️ 必须：delete p;否则 内存泄漏

✅ 方案 4（C++11+）：智能指针 ✅✅✅

#include <memory>
std::unique_ptr<int> func() {
    return std::make_unique<int>(10);//应尽量避免裸指针管理资源。
}

❓ 为什么返回 int可以，返回 int*就不行？

返回 int→ 返回的是 值的拷贝

返回 int*→ 返回的是 地址，但地址指向的东西没了

总结：永远不要返回局部变量的指针或引用。

指针传递、值传递、引用传递

值传递（Pass by Value）

✅ 定义：把实参的“拷贝”传给函数，函数内操作不影响原变量。

🔍 内存本质：形参是实参的副本；会调用 拷贝构造函数；修改形参不会影响原变量

void func(int x) {
    x = 10;
}

int main() {
    int a = 5;
    func(a);// a 仍然是 5
}

✅ 优点：安全；无副作用

❌ 缺点：效率低（大对象拷贝成本高）；无法修改原数据

对于内置类型（int、double）推荐值传递；对于大对象，避免值传递。

指针传递（Pass by Pointer）

✅ 定义：把变量的地址传给函数，通过指针间接修改原变量。

🔍 内存本质：传递的是 地址值；形参是一个指针变量；可通过 *p修改原变量

void func(int* p) {
    *p = 10;
}

int main() {
    int a = 5;
    func(&a);// a == 10
}

✅ 本质仍是值传递（地址值）✅ 必须判空✅ 可以为 nullptr ❌ 可读性较差

指针传递本质是值传递，只不过传的是地址。

引用传递（Pass by Reference）

✅ 一句话定义：给实参起一个别名，函数内操作直接影响原变量。

🔍 内存本质：不创建新对象；编译器通常实现为 常量指针；语法层面更安全

void func(int& x) {
    x = 10;
}

int main() {
    int a = 5;
    func(a);// a == 10
}

❌ 不可以为空 ❌ 不需要判空 ❌ 不可以重新绑定 ✅ 非常推荐

引用传递兼具效率与安全性，是现代 C++ 的首选。

对比

对比项 值传递 指针传递 引用传递
是否拷贝 ✅ 是 ✅ 是（地址） ❌ 否
能否改原值 ❌ 否 ✅ 能 ✅ 能
是否可为空 ❌ ✅ ❌
安全性 ✅ 高 ❌ 低 ✅ 高
可读性 ✅ 好 ❌ 差 ✅ 好
典型用途 小对象 动态内存 / 可选参数 普通参数

追问

❓ 引用传递比指针传递好在哪里？

✅ 答案：无需判空；语法简洁；不易出现野指针；更符合现代 C++ 风格

❓ 引用传递真的不占内存吗？

✅ 标准回答：语法层面不占内存，但底层通常由编译器用指针实现。

❓ 什么时候必须用指针传递？

✅ 答案：需要表示“无对象”（nullptr）；需要改变指针本身指向；与 C API 交互

RAII 思想

RAII 的核心思想是：用对象的生命周期来管理资源。

核心原则（4 句话）:把资源封装进对象;构造函数中获取资源;析构函数中释放资源；对象离开作用域时自动释放

📌 本质： 让编译器帮你管理资源

✅ 手写一个 RAII 类

class FileRAII {
public:
    FileRAII(const char* name) {
        fp = fopen(name, "r");
    }
    
    ~FileRAII() {
        if (fp) {
            fclose(fp);
            fp = nullptr;
        }
    }

private:
    FILE* fp;
};

C++ 标准库中的 RAII

资源 RAII 类型
内存 std::unique_ptr, std::shared_ptr
文件 std::fstream
互斥锁 std::lock_guard, std::unique_lock
线程 std::thread

📌 RAII 提供 基本异常安全保证

补充：✅ 异常安全级别

级别 说明
基本保证 不泄漏资源
强保证 操作要么成功，要么回滚
不抛异常 noexcept

❓ RAII 和 GC（垃圾回收）的区别？

✅ 标准回答：

RAII 是确定性的资源管理，析构时机明确；GC 是非确定性的，无法及时释放文件、锁等资源。

C++ 追求零开销抽象，RAII 能在编译期保证资源释放，性能更高，控制更精确。

智能指针深入解析

智能指针的本质：用 RAII 管理堆内存，把 delete 交给编译器。通过对象生命周期自动释放资源，解决裸指针的内存安全问题。

裸指针的问题：忘记 delete——内存泄漏；提前 return / throw——泄漏；多次 delete——未定义行为；异常不安全——资源泄漏

std::unique_ptr（独占所有权）：一份资源，只有一个拥有者

std::unique_ptr<int> p = std::make_unique<int>(10);

❌ 不能拷贝✅ 只能移动

拷贝会导致双重释放（double free）

std::unique_ptr<int> p1 = std::make_unique<int>(10);
std::unique_ptr<int> p2 = std::move(p1);// p1 == nullptr

✅ 默认首选 ✅ 性能零额外开销 ✅ 禁止滥用 shared_ptr

std::shared_ptr（引用计数）：多个指针共享同一份资源

std::shared_ptr<int> p1 = std::make_shared<int>(10);
std::shared_ptr<int> p2 = p1;

❓引用计数是怎么实现的？

✅ 控制块（Control Block）

shared_ptr
┌──────────────┐
│  ptr ────────┼─► 资源
│  control ────┼─► [strong_ref | weak_ref]
└──────────────┘

强引用计数：决定资源是否释放

弱引用计数：决定控制块是否释放

❓make_sharedvs new

shared_ptr<int> p(new int(10));//❌ 不推荐
auto p = make_shared<int>(10);//✅ 推荐

异常安全:防止构造失败泄漏;一次分配:减少内存碎片;性能更好:控制块 + 对象一起分配

❓引用计数是否是线程安全的？

✅ 是的，引用计数的增减是 原子操作，但对象本身的线程安全仍需你自己保证

std::weak_ptr（解决循环引用）

// 循环引用
struct B;

struct A {
shared_ptr<B> b;
};

struct B {
shared_ptr<A> a;
};// ❌ 引用计数永远不为 0 → 内存泄漏

struct B {
weak_ptr<A> a;  
};// ✅ weak_ptr 不增加引用计数

使用 weak_ptr

if (auto sp = wp.lock()) {
    // 安全访问
}

智能指针的底层实现

1️⃣ shared_ptr 简化模型

template<typename T>
class shared_ptr {
    T* ptr;
    ControlBlock* cb;
};
struct ControlBlock {
    atomic<int> strong_count;
    atomic<int> weak_count;
};

2️⃣ 析构顺序

  1. strong_count–
  2. 若为 0 → 释放 资源
  3. weak_count–
  4. 若为 0 → 释放 控制块

追问

❓ shared_ptr 一定比 unique_ptr 慢吗？

✅ 是的。原子操作，控制块访问

❓ 可以把 unique_ptr 转成 shared_ptr 吗？

✅ 可以

unique_ptr<int[]> p = make_unique<int[]>(10);

总结：C++ 智能指针基于 RAII 思想， unique_ptr表示独占所有权，无额外开销； shared_ptr通过引用计数实现共享，线程安全但代价更高； weak_ptr用于打破循环引用；

优先使用 make_shared/ make_unique， 能用 unique_ptr就不用 shared_ptr。

weak_ptr能打破循环引用

它不增加引用计数，只“观察”资源，不“拥有”资源。

struct B;

struct A {
    shared_ptr<B> b;
};

struct B {
    shared_ptr<A> a;
};

auto pa = make_shared<A>();
auto pb = make_shared<B>();

pa->b = pb;
pb->a = pa;

🔴 引用计数变化

A：2（pa + B::a）

B：2（pb + A::b）

当 pa、pb离开作用域：

A 的计数从 2 → 1（B 还指着它）

B 的计数从 2 → 1（A 还指着它）

永远无法归零 → 内存泄漏

✅ weak_ptr 是不控制对象生命周期的智能指针

✅ 不增加 强引用计数 ✅ 只增加 弱引用计数 ✅ 不影响对象析构

控制块结构：

Control Block:
┌──────────────┐
│ strong_ref   │ ← shared_ptr 控制
│ weak_ref     │ ← weak_ptr 控制
└──────────────┘

📌 对象销毁只看 strong_ref

struct B;

struct A {
    shared_ptr<B> b;
};

struct B {
    weak_ptr<A> a;   // ✅ 改用 weak_ptr
};

🔴 引用计数变化

A：1（只有 pa）

B：2（pb + A::b）

当 pa、pb离开作用域：

pa销毁 → A 的 strong_ref 从 1 → 0

A 被销毁

B 的 strong_ref 从 2 → 1

pb销毁 → B 的 strong_ref → 0

B 被销毁✅ 完美释放，无泄漏

❓weak_ptr 如何访问对象？

✅ 必须通过 lock()

if (shared_ptr<A> sp = wp.lock()) {
    // 安全使用
}

lock() 结果为空，表示对象已销毁

📌 这是 weak_ptr 的安全使用方式

总结： 循环引用致命的根源是“互相强引用”， weak_ptr 切断了其中一条强引用链。

循环引用的本质是多个 shared_ptr 互相持有，导致强引用计数永远不为零。

weak_ptr 不增加强引用计数，只观察对象，不影响对象生命周期。

将循环中的任意一个 shared_ptr 改为 weak_ptr，即可打断强引用环，使对象能被正常释放。

✅ weak_ptr 不保证对象存在

✅ weak_ptr 常用于缓存、观察者模式

✅ weak_ptr 可以检测对象是否存活

✅ weak_ptr 不会阻止内存回收

malloc 维护 空闲内存块链表

free 时合并相邻空闲块

[ size | magic | 内存块 ]

用户拿到的是 data部分

free 时通过指针偏移找到头部

void* p = malloc(1);

实际分配可能是 16 / 32 字节

✅ 原因：CPU 访问对齐内存更快；方便管理

❓free 真的把内存还给 OS 了吗？

❌ 不一定！

free(p);

通常只是：标记为空闲；加入空闲链表；并不立即归还 OS

📌 这就是为什么：程序内存占用只会涨不会降

❓malloc / free 的四大问题

  1. 内存泄漏——忘记 free
  2. 野指针——free 后继续使用
  3. 重复释放——double free
  4. 内存碎片——小块残留

malloc/free 是手动管理，容易产生碎片和安全问题，因此现代 C++ 推荐使用 RAII 和智能指针。

❓malloc 与 new 的区别

对比 malloc / free new / delete
语言 C / C++ C++
构造 / 析构 ❌ ✅
类型安全 ❌ ✅
失败行为 返回 NULL 抛异常
重载 ❌ ✅
✅ new 底层通常调用 malloc，但会额外调用构造函数。

追问

❓内存分配器

分配器 特点
ptmalloc glibc 默认
jemalloc FreeBSD / Firefox
tcmalloc Google，高性能

📌为什么服务器程序要用 jemalloc / tcmalloc？ ✅ 减少锁竞争 + 降低碎片

❓ malloc(0) 返回什么？ ✅ 返回一个可 free 的非空指针（实现定义）

❓ free(NULL) 会怎样？ ✅ 什么都不做（安全）

❓ 为什么 free 不需要大小？ ✅ 因为 malloc 在头部记录了大小

malloc、new，free、delete 区别（汇编层）

对比维度 malloc / free new / delete
汇编本质 库函数调用 库函数调用 + 构造/析构
是否直接 syscall ❌ 否 ❌ 否
是否调用构造函数 ❌ 否 ✅ 是
是否调用析构函数 ❌ 否 ✅ 是
失败行为 返回 NULL 抛出 std::bad_alloc
底层实现 通常调用 malloc 通常调用 operator new
📌 一句话总结：new/delete 是 malloc/free 的 C++ 封装 + 语义增强。

✅ 关键差异： operator new≠ malloc（但默认实现调用 malloc）

构造发生在分配之后，new = operator new + 构造函数

delete先析构（如果有），delete = 析构函数 + operator delete

总结：
在汇编层，malloc/free 是纯内存管理函数；

new/delete 是在其之上的 C++ 语义封装，额外承担构造、析构和异常安全责任；

对于非 POD（Plain Old Data）类型，绝不能用 malloc/free 替代 new/delete。

补充：POD 类型是指：兼容 C 语言、具有平凡的内存布局和构造/析构行为的类型。📌 简单理解：“像 C 结构体一样的 C++ 类型”

内存泄露如何检测和避免

内存泄漏是指：程序动态分配的内存，在使用完毕后没有释放，也无法再被访问，导致内存持续增长。

📌 注意：不是立刻崩溃,是慢性死亡

常见来源：

类别 示例
忘记 delete / free new后没 delete
异常路径跳过释放 throw/ return
指针被覆盖 原始指针丢失
容器增长 vector/ map无限 push
循环引用 shared_ptr互指
第三方库 接口使用不当

如何检测：

1️⃣ 工具级检测

工具 平台 特点
Valgrind Linux 行业标准
AddressSanitizer GCC/Clang 快、准
Visual Studio Windows CRT 检测
LeakSanitizer LLVM 集成于 ASan

🔥 AddressSanitizer

g++ -fsanitize=address -g main.cpp

✅ 优点： 速度快 ；精确定位代码行

2️⃣ 代码级检测

✅ 重载 new / delete

void* operator new(size_t size) {
    void* p = malloc(size);
    record_allocation(p);
    return p;
}

3️⃣ 静态分析工具
Clang Static Analyzer

Coverity

SonarQube

📌 静态分析能发现“不可能路径上的泄漏”。

如何避免

1️⃣ RAII（第一原则）:资源获取即初始化，永远不要裸 new

2️⃣ 交给对象生命周期管理

3️⃣ 使用智能指针

4️⃣ 避免循环引用

5️⃣ 使用 STL 容器

追问

❓ new 了没 delete 一定是内存泄漏吗？

✅ 不一定，程序退出后 OS 会回收，但长期运行的程序（服务）是致命的

❓ 内存泄漏会导致什么问题？

✅ 内存持续增长 ；OOM（Out of Memory）；服务重启；性能下降

❓ Valgrind 能检测所有泄漏吗？

❌ 不能 ，无法检测第三方库 ，对共享内存有限

野指针和空悬指针

野指针（Wild Pointer）：指针变量未被初始化，指向一个随机地址。

常见产生方式：

  1. 未初始化（int* p;）
  2. 被优化掉（寄存器指针）；
  3. 越界访问（arr[i]越界）

空悬指针（Dangling Pointer）：指针指向的对象已经被销毁，但指针仍保留原地址。

常见产生方式：

  1. delete 后继续使用：delete p; *p;
  2. 返回局部变量地址：return &local;
  3. 容器元素被 erase：vector::erase
  4. 智能指针 reset：shared_ptr.reset()

一样危险，但空悬指针更隐蔽

✅ 防野指针

int* p = nullptr;   // ✅初始化指针

✅ 防空悬指针

delete p;
p = nullptr;        // ✅及时置空

✅ 终极解决方案 ：RAII + 智能指针

❓ 智能指针会产生空悬指针吗？

unique_ptr ❌ shared_ptr ❌

weak_ptr必须通过 .lock()来生成一个 shared_ptr，以此确保在访问对象的那一瞬间对象还活着，从而避免产生空悬指针。

weak_ptr<int> wp;

{
    shared_ptr<int> sp = make_shared<int>(10);
    wp = sp;
} // sp 离开作用域，对象被销毁

// wp 现在指向一个已经死亡的对象（空悬指针）
if (!wp.expired()) {
    // 危险！在 expired() 检查之后，对象可能又被释放了
    // *wp.lock() 在这里可能失败
}

✅ lock()的原子性

lock()不仅仅是“返回一个指针”，它是一个 原子操作：

  1. 检查 控制块中的强引用计数。
  2. 如果对象还活着，立即将强引用计数 +1。
  3. 返回一个有效的 shared_ptr。

✅ 正确用法（防空悬指针）
weak_ptr wp;

{
    shared_ptr<int> sp = make_shared<int>(10);
    wp = sp;
}

// ✅ 正确：通过 lock() 获取临时所有权
if (shared_ptr<int> sp = wp.lock()) {
    // 此时 sp 持有了对象
    // 在这个作用域内，对象绝对不会被释放
cout << *sp << endl;
} else {
    // 对象已经死了，安全处理
    cout << "Object is gone." << endl;
}

补充：

对比：expired()vs lock()

方法 行为 是否安全
wp.expired() 只检查对象是否还活着 ❌ 不安全（有竞态）
wp.lock() 尝试获取对象 + 增加引用 ✅ 安全

📌永远不要单独使用 expired()来判断对象是否存在，因为判断之后对象可能立即被释放。必须使用 lock()来获取一个 shared_ptr，从而保证在持有 shared_ptr期间对象是安全的。

调用 lock()时原子性地读取并增加强引用计数，正是因为 “检查”和“增加计数”是不可分割的一步，才避免了空悬指针。

关联知识：

shared_from_this()：在类的成员函数中安全地获取自身的 shared_ptr，避免手动管理 this。

enable_shared_from_this：常与 weak_ptr配合使用，解决回调中对象已释放的问题。

常见的 C/C++ 内存错误

主要可分为非法访问、生命周期管理和多线程并发三大类。

非法访问类错误（读写违例）

这类错误发生在访问不属于进程地址空间或受保护的内存时。

错误类型 核心成因 典型代码示例 关键点
缓冲区溢出 读写超出数组边界，覆盖相邻内存。 char s[10]; strcpy(s, "too_long_string"); 可能导致栈破坏（Stack Smashing），是安全漏洞（如栈溢出攻击）的根源。
段错误 (SIGSEGV) 解引用空指针、已释放内存或未映射地址。 int *p = nullptr; *p = 1; 操作系统为了保护进程而强制终止。需区分是野指针还是空悬指针导致的。
内存越界 下标计算错误或循环条件失误。 int arr[10]; for(int i=0; i<=10; i++) arr[i]=i; 不仅是数组，还包括 std::string 的 c_str() 写入越界。

生命周期与管理类错误（逻辑缺陷）

这类错误源于对内存“生老病死”的控制不当，通常表现为内存泄漏或重复释放。

错误类型 核心成因 典型代码示例 关键点
内存泄漏 (Memory Leak) 失去了对已分配内存的引用，无法释放。 void f() { int* p = new int; } 长期运行的服务（Server）最忌讳。需区分堆泄漏和系统资源泄漏（句柄、文件描述符）。
双重释放 (Double Free) 对同一块内存执行两次 free/delete。 delete p; delete p; 会破坏堆的管理结构，导致程序崩溃或堆污染。
不匹配释放 分配与释放方式不一致。 int* p = new int[10]; delete p; 必须 new[] 配 delete[]，malloc 配 free。混用会导致未定义行为。
循环引用 shared_ptr 相互持有，引用计数永不为0。 A.ptr = B; B.ptr = A; 必须用 weak_ptr 打破循环，这是现代 C++ 的高频考点。

未初始化与多线程错误

错误类型 核心成因 说明
使用未初始化内存 变量声明后未赋值即读取。 栈内存的值是随机的，可能导致逻辑不可控。
数据竞争 (Data Race) 多线程无同步读写同一块内存。 属于未定义行为，即使使用智能指针，若对象内部数据无锁保护，依然会出错。

错误检测与防御策略

场景 工具/方法 说明
运行时检测 AddressSanitizer (ASan) 比 Valgrind 快得多，能精准定位越界和 UAF。
运行时检测 Valgrind (Memcheck) 老牌内存分析神器，但性能损耗大。
编码防御 RAII / 智能指针 杜绝裸指针管理资源，从根源上消除泄漏和双重释放。
编码规范 STL 容器优先 尽量使用 std::vector, std::string 代替原生数组。

除了关注堆内存，还需注意 栈溢出（递归过深或超大局部变量）以及 内存碎片（频繁申请释放不同大小的内存块导致无法分配大块连续内存）的问题
