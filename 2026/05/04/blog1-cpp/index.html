对齐规则（重点）
✅ 通用规则（最常见）

基本类型对齐值 = 自身大小

char→ 1 字节
short→ 2 字节
int→ 4 字节
double→ 8 字节

每个成员的对齐值 = 👉 min(自身大小, 编译器默认对齐值)（通常默认 4 或 8（64位常见））

结构体对齐值 = 成员中最大对齐值，结构体总大小必须是其对齐值的整数倍

struct A {
    char c;     // 1 字节
    int i;      // 4 字节
};

偏移量：  0   1   2   3   4   5   6   7
      [c] [pad] [pad] [pad] [i][i][i][i]

sizeof(struct A) == 8 //📌 char后面填充 3 个字节

结构体嵌套的对齐规则：按自身最大成员对齐

struct Inner {
    double d;   // 8
    char c;     // 1
};

struct Outer {
    int i;      // 4
    struct Inner in;
};

Outer对齐值 = max(4(int), 8(struct Inner)) = 8

sizeof(struct Outer) == 24（常见结果）

#pragma pack 的影响

#pragma pack(1)
struct D {
char c;
int i;
};
#pragma pack() // 恢复默认对齐
// #pragma pack(pop)是 弹出之前保存的对齐
sizeof(struct D) == 5

📌 常用于： 网络通信 协议数据 二进制存储

⚠️ 缺点：性能下降、引发平台问题

结构体成员应按“对齐值从大到小”排列，以减少内存补齐，提高内存利用率和访问效率。

struct X {
    char c;
    int i;
    short s;
};
//[c][pad*3][i*4][s*2][pad*2]
//sizeof = 12
struct Y {
    int i;
    short s;
    char c;
};
//[i*4][s*2][c][pad]
//sizeof = 8

结构体内部成员的补齐，是按“自身对齐值”来的，不是统一补齐到结构体中最大的那个类型。

3️⃣ externvs extern "C"

这是链接层面的区别。

extern—— 外部声明，和static一类属于存储类说明符（变量在哪里、活多久）

extern “C”—— C语言链接，属于链接说明符（怎么找这个函数名）

关键字 层级 作用
extern 变量/函数 声明变量/函数在其他编译单元定义
extern “C” 链接规范 禁用 C++ 的 name mangling（名称修饰） 
// 告诉 C++ 编译器：这个函数是用 C 写的，别改名
#ifdef __cplusplus
extern "C" {
#endif

void c_function();

#ifdef __cplusplus
}
#endif

补充：extern “C”—— C语言链接

一句话：关闭 C++ 的名称修饰（Name Mangling），以便链接 C 语言编译的库。

深度解析：

C++ 为了支持函数重载，会把函数名改成类似 _Z1fv这样的符号。

C 语言没有重载，函数名就是 _f。

当 C++ 代码调用 C 库（如 printf）时，必须用 extern “C”告诉编译器：“这个函数是用 C 规则编译的，请按 C 规则去找名字”。

4️⃣ explicit：单参数构造函数的守护者：防止构造函数进行隐式类型转换。

class A {
public:
    explicit A(int x) {} // 禁止隐式转换
};

A a = 10; // ❌ 编译错误
A b(10);  // ✅ OK

📌 如果不加 explicit，可能会导致意想不到的函数重载匹配。

现代 C++ 建议：对于所有单参数的构造函数（除非你明确想要隐式转换），一律加上 explicit。C++11 后，它也适用于多参数构造函数（防止列表初始化时的隐式转换）。

5️⃣ mutable：打破 const 的特例：允许在 const成员函数中修改成员变量。

一句话：突破 const限制，允许在 const成员函数中修改成员变量。

深度解析：

被 mutable修饰的变量，不受 const成员函数的约束。

class Data {
public:
    int getValue() const {
        mutex_.lock(); // OK: mutable 允许在 const 函数中修改
        // ...
        mutex_.unlock();
        return value_;
    }
private:
    int value_;
    mutable std::mutex mutex_; // 逻辑上不改变对象状态，但需要修改
};

典型用途：缓存（Cache）、互斥锁（Mutex）、调试计数。

📌 使用场景：缓存、日志计数、互斥锁（mutex）等不影响对象逻辑状态的字段。

强制类型转换

能用 C++ 四种 cast，就不要用 C 风格 (Type)value强转。

转换 英文 核心用途 是否安全
static_cast 静态转换 良性转换（数值、父子类） ✅ 相对安全
dynamic_cast 动态转换 多态类型安全检查 ✅ 最安全
const_cast 常量转换 去掉 / 加上 const ⚠️ 高风险
reinterpret_cast 重解释转换 底层比特重解释 ❌ 极危险

1️⃣ static_cast（最常用）

✅ 编译期转换，无运行时开销

double d = 3.14;
int i = static_cast<int>(d);   // ✅3

class Base {};
class Derived : public Base {};

Base* b = new Derived();
Derived* d = static_cast<Derived*>(b); // ✅

int* p = static_cast<int*>(b); // ❌ 无关类型

用于相关类型之间的转换，编译期检查，不能去除 const。

2️⃣ dynamic_cast（多态专用）

✅ 运行时类型检查（RTTI）

class Base {
public:
    virtual ~Base() {} //必须有虚函数✅
};

class Derived : public Base {};

Base* b = new Derived();
Derived* d = dynamic_cast<Derived*>(b);

✅ 成功：返回非空指针

❌ 失败：返回 nullptr（指针）或抛异常（引用）

❌ 没有虚函数 → 编译失败

❓dynamic_cast 为什么要求基类有虚函数？

✅ 因为需要 RTTI（运行时类型信息）

3️⃣ const_cast（最容易被误用）

✅ 唯一能改 const / volatile 的转换

const int x = 10;
int* p = const_cast<int*>(&x); //✅

*p = 20; // ❌ 未定义行为（UB）

const_cast用于移除 const，但修改真正的 const 对象是未定义行为。

int real_value = 10;          // 原始变量不是 const
const int& ref = real_value;  // 只是通过 const 引用“承诺”不改

int* p = const_cast<int*>(&ref);
*p = 20;                     // ✅ 安全，real_value 变为 20

4️⃣ reinterpret_cast（最底层）

✅ 重新解释比特位

int x = 0x12345678;
char* p = reinterpret_cast<char*>(&x);

📌 常用于：网络协议；硬件寄存器；序列化

❓reinterpret_cast是安全的？ ❌它不做任何检查，完全依赖程序员。

与 C 风格强制转换对比

int* p = (int*)&x; // C 风格

❌ 问题：编译器不告诉你做了什么；可能偷偷调用 const_cast+ static_cast

int* p = static_cast<int*>(...); //✅ C++ 推荐写法

总结：
static_cast用于相关类型的静态转换；

dynamic_cast用于多态类型的安全向下转型（需 RTTI）；

1. sizeof：对象有多大？

它回答的问题是：“这个变量或类型需要占用多少个字节？”

关键点：sizeof(MyStruct) 是 8，而不是 1+4=5。这是因为编译器为了效率，会在 char 后面插入 3 个填充字节，让 int i 的地址对齐到 4 的倍数。sizeof 包含这些填充字节。

2. alignof：对象要放在哪里？

它回答的问题是：“这个类型的地址必须是几的倍数？”

现代 CPU 访问内存时，如果数据的地址是其自然对齐要求的倍数，访问速度最快。例如，int 通常要求 4 字节对齐。

关键点：

  • alignof(int) 通常是 4，意味着 int 变量的地址必须是 4 的倍数（如 0x0004, 0x0008）。
  • alignof(MyStruct) 是 4。结构体的对齐要求等于其所有成员中对齐要求最严格的那个。这里 int 要求 4，所以整个结构体也要按 4 对齐。这也解释了为什么 sizeof 的结果是 8（末尾可能也有填充，以保证数组中下一个元素也能正确对齐）。

空类的sizeof是多少

在 C++ 中，空类的 sizeof 结果是 1（在大多数主流编译器如 GCC、Clang、MSVC 中）。

为什么不是 0？

这是 C++ 标准明确规定的，主要有两个核心原因：

1. 确保对象具有唯一的地址（对象唯一性）

C++ 要求每个独立的对象都必须有一个独一无二的地址。如果空类的大小为 0，就会出现以下问题：

如果 sizeof(Empty) 是 0，那么 a 和 b 可能会分配到同一个内存地址，导致无法区分这两个不同的对象。分配 1 个字节可以确保每个实例都有自己的地址。

2. 数组分配的要求

如果 sizeof(Empty) 是 0，那么 arr 将不占用任何空间，arr[0] 和 arr[1] 的地址将相同，这违反了数组元素必须连续存储且地址不同的基本原则。大小为 1 保证了数组中的每个元素都有正确的偏移量（&arr[i] == &arr[0] + i * sizeof(Empty)）。

深入细节：空基类优化 (EBO)

虽然空类本身的大小是 1，但在继承场景下，编译器会进行一种重要的优化：空基类优化 (Empty Base Optimization, EBO)。

原因：当空类作为基类时，编译器不会为空基类子对象分配那额外的 1 个字节。Derived 的大小仅由其成员 x（4 字节）和对齐规则决定。这是 C++ 标准中允许打破“空类大小为 1”规则的少数特例之一。

特殊情况：带成员的空类

如果一个类虽然看起来“空”，但有成员函数、类型别名或静态成员，它的大小依然是 1。因为这些成员不存储在对象实例的内存布局中。

5. 为什么这种设计很“妙”？

  1. 零开销抽象：当删除器是无状态（Stateless）的时候，std::unique_ptr 在内存占用上完全等同于一个裸指针 T*。
  2. 性能无损：调用删除器 deleter(ptr) 时，因为 deleter 是基类（或基类的成员），编译器可以直接内联这个函数调用，没有任何间接寻址的开销。
  3. 灵活性：当删除器是有状态（Stateful，比如需要引用计数或自定义内存池句柄）时，它自动退化为成员变量，虽然体积变大了，但功能依然正常。

  • 利用 空基类优化 (EBO) 让空删除器不占空间。
  • 利用 RAII 保证资源释放。

核心痛点：共享所有权

unique_ptr 之所以能瘦，是因为它知道：“我是这个指针的唯一主人。”
shared_ptr 不行，它必须时刻准备着回答两个问题：

  1. 还有几个人在用这个资源？（强引用计数）
  2. 还有没有人监视着这个资源？（哪怕不用它，只是在观察）（弱引用计数）

为了解决这两个问题，shared_ptr 引入了一个核心概念：控制块（Control Block）。

1. 内存布局：指针 + 控制块

一个典型的 std::shared_ptr 对象内部通常包含两个指针（这是它通常是 16 字节的原因）：

  1. 托管对象指针 (T*): 指向实际的数据（如 int）。
  2. 控制块指针: 指向堆上的一块数据，里面包含了引用计数等信息。

2. 为什么不能像 unique_ptr 那样用 EBO？

unique_ptr 能把删除器“压”进基类，是因为删除器是编译期绑定的（unique_ptr<int, MyDeleter> 的类型本身就包含了 MyDeleter）。
shared_ptr 做不到，因为：

  1. 引用计数必须在堆上：多个 shared_ptr 实例分布在内存的不同角落，它们必须共享同一份计数。唯一的办法就是把计数放在堆上。
  2. 类型擦除 (Type Erasure)：shared_ptr 支持拷贝构造，甚至可以从 unique_ptr 转换过来。这意味着 shared_ptr 内部存储的删除器，在编译期不一定是确定的类型（它可能被包装在一个 std::function 类似的机制里）。为了支持这种灵活性，删除器必须存在于运行时的控制块中，而不能作为模板参数被 EBO 优化掉。

5. 为什么说 shared_ptr 是“性能杀手”？

除了体积大，它还有隐形成本：

  1. 原子操作开销：每次拷贝或析构，都要执行原子递增/递减指令（CAS 操作），这在高并发下是昂贵的。
  2. 控制块访问：每次解引用，理论上都要通过控制块检查是否合法（虽然编译器会优化，但逻辑上存在）。
  3. 内存碎片：频繁分配和释放控制块可能导致内存碎片。

经典陷阱：循环引用

这也是 shared_ptr 特有的坑，直接导致内存泄漏。

解决方法是使用 std::weak_ptr（它只观察，不增加强引用计数）。

一句话总结

  • unique_ptr 是极致的内敛：能用编译期解决的绝不留到运行期，能用继承压缩的绝不占空间。
  • shared_ptr 是周全的管家：为了支持共享、弱引用和线程安全，它不得不引入控制块，从而牺牲了体积和速度。

设计哲学：能用 unique_ptr 就别用 shared_ptr。除非你真的需要共享所有权，否则 shared_ptr 的那 16 字节和原子操作开销是不值得的。

constexpr和static const有区别吗

有区别，而且区别很大。 虽然在很多简单场景下它们看起来效果一样，但在求值时机、内存处理、能力和现代 C++ 设计理念上完全不同。

简单总结一句话：

constexpr 强调“编译期常量”，static const 强调“运行期只读”。

下面从 5 个维度详细区分，并给出选型建议。

一、核心区别一览表

求值时机 编译期（必须） 运行期（通常）
是否能用于数组大小 ✅ 可以 ❌（C++11 前不行，C++11 后有限支持）

二、本质区别详解

1️⃣ 求值时机（最关键）

constexpr：编译期常量

  • 编译器在编译阶段就计算出结果。
  • 不生成任何运行时代码。
  • 可视为“字面量”。

static const：运行期只读

  • 语义上是“只读变量”。
  • 在 C++11 之前，不能保证是编译期常量。
  • 是否真的在编译期求值，取决于编译器和优化级别。

2️⃣ 能否作为常量表达式（Constant Expression）

  • constexpr 保证是常量表达式。
  • static const 只有在满足“整数常量表达式”条件时才行。

3️⃣ 模板参数中的表现

  • constexpr 永远可以作为非类型模板参数。
  • static const 只有在整数类型 + 有定义的情况下才行。

4️⃣ 内存占用与 ODR（一次定义规则）

static const（类内）

  • 可能在目标文件中生成符号。
  • 取地址时会强制分配内存。

constexpr

  • 不取地址时通常不占内存。
  • 更符合“值语义”。
