手写Sobel边缘检测后处理Pass

以「在 UE 5.7.4 源码里插入一个后处理 Pass，对场景色做 Sobel 边缘检测」为例， 逐文件、逐行地把 RDG（Render Dependency Graph） 全屏后处理 Pass 的完整写法讲清楚。

目标

在场景渲染完成后、后处理（TAA / Tonemap）之前，插入一个 Pass， 把场景色采样成一张「黑底白边」的 Sobel 边缘图，再让下游后处理把它当作新的场景色继续处理。 最终你会在画面上看到物体轮廓被描边。

核心概念

什么是RDG Pass

UE 的渲染不再直接调 RHICmdList.Drawxxx，而是「先用 FRDGBuilder 把一堆 Pass 描述成一张依赖图， 最后由 RDG 统一调度、合批、剔除」。你写的不是一个「立刻执行」的函数，而是一段「往图里加一个节点」的描述。

关键推论：

创建的纹理（GraphBuilder.CreateTexture）只是图里的节点，真正的内存分配由 RDG 在调度时做。

没有被任何下游消费的中间纹理，会被 RDG 自动剔除（cull） 掉——这是后面「看不到效果」的头号嫌疑人。

全屏 Pass 的「顶点」由引擎 helper 代劳，你只写像素着色器。

Global Shader（全局着色器）

我们的 Sobel 像素着色器是一个 FGlobalShader：它不绑定任何材质 / 顶点工厂， 是引擎全局唯一、与场景无关的 shader。颜色后处理、拷贝、降采样等都属于这一类。 IMPLEMENT_GLOBAL_SHADER 把它和 .usf 里的入口函数绑定起来。

Full-screen Pass 的「顶点从哪来」

全屏 Pass 需要一个覆盖整个屏幕的三角形/四边形。引擎提供两套做法：

FPixelShaderUtils::AddFullscreenPass —— 内部用 FScreenVertexShaderVS（只输出 SV_Position）+ DrawFullscreenTriangle。本文采用这套。
FPostProcessVS + DrawRectangle —— 会输出 TEXCOORD0 UV。

⚠️ 这两套的顶点着色器输出不同，直接决定你的像素着色器能不能声明 UV 输入

数据流

用一句话概括：我们读场景色 → 画到临时 RT → 把结果原地拷回场景色 → 下游后处理照常处理这张被改过的场景色 → 上屏。

关键纪律：不要去碰 ViewFamilyTexture。它就是 backbuffer（最终上屏目标）。 一旦把它重定向到离屏纹理，这一帧 backbuffer 根本没被写，画面会「卡在上一帧」，看起来像什么都没发生。

文件一：像素着色器 SobelEdgePS.usf

头部与include

注意用的是 绝对虚拟路径 /Engine/Private/Common.ush，不是相对路径 “Common.ush”。

引擎内部 shader 能直接 #include “Common.ush” 是因为它们本身就位于 /Engine/Private/ 映射根下；

我们的 .usf 处于插件/手写映射根，相对路径解析不到，必须写绝对虚拟路径。

资源 / uniform 声明（名字必须和 C++ 的 FParameters 对应）

这些全局变量不是随便起的名——SHADER_PARAMETER_* 宏在 C++ 侧按 名字 把它们和 FParameters 成员绑定。 名字写错，C++ 传了值 shader 也收不到。

入口函数：UV 从 SV_Position 反算

为什么不能写 in float2 UV : TEXCOORD0？ 因为我们用 AddFullscreenPass → 顶点着色器是 FScreenVertexShaderVS，它只输出 SV_Position，根本不输出 TEXCOORD0。

若 PS 声明 TEXCOORD0 输入而 VS 没给，VS/PS 签名不匹配 → D3D12 PSO 创建失败（E_INVALIDARG）。

调试隔离开关

先把「效果对不对」和「管线通不通」解耦：Mode 1 全屏红说明整条链路没问题；

Mode 2 平滑红→黄、下→绿说明 UV 采样坐标正确；只有 Mode 0（默认）才是真 Sobel。

以后你写任何后处理，都建议先放一个纯色/渐变开关，用它把「没跑」和「算错」分开。

Sobel 算子本体

邻域采样用 UV + float2(±t.x, ±t.y) 正好偏移一个像素，Sobel 就是要比较「左/右」「上/下」的亮度差。

七、为什么你之前 OutlineBlend.usf 容易出问题？

很多自定义 Outline Shader 会犯这些错：

❌ 用 UV 当屏幕坐标
❌ 没用 SV_Position，导致边缘抖动
❌ 在 VS 里改了 Position，但没理解它会影响 SV_Position
❌ 在 PS 里试图修改 SV_Position（这是非法的）

八、一张对比表（面试 / Debug 必背）

名字 阶段 坐标空间 是否可写 典型用途
Position VS 输入 NDC / 裁剪 ✅ 定义顶点

SV_Position PS 输入 屏幕像素 ❌ 像素位置
UV VS / PS [0,1] ✅ 采样贴图

九、一句话记忆法

Position 决定“顶点在哪”，SV_Position 决定“像素画在哪”，UV 决定“贴图采哪”。

0. 目标

当你想给画面加一个自定义全屏后效（调色、暗角、描边、扫描线、屏幕扭曲……），UE 有三条路线：

路线 是否改引擎 适合 缺点
A. Post Process Material 不改 调色、简单全屏滤镜，最快验证 复杂算法/额外纹理/RDG 受限
B. Plugin + SceneViewExtension + GlobalShader 不改 Engine/ 源码 需要自定义 HLSL / RDG / 可长期维护 要多写几个类
C. 直接改 Renderer 内置 PostProcess pass 改引擎 必须做成引擎内置节点 合并成本高、升级痛苦

本插件走 B：它把”暗角”做成一个独立插件，通过 SceneViewExtension 把自己的全屏 Pass 插入到引擎后处理管线的指定位置。对引擎零侵入，可随工程带走、可上版本控制。

3. 核心原理：调用链

引擎每帧渲染到后处理阶段时，会遍历所有已注册的 SceneViewExtension，并对每一个后处理节点（EPostProcessingPass）调用它们的 SubscribeToPostProcessingPass。我们的扩展在 AfterDOF 这个节点挂了一个回调，回调里把我们的全屏暗角 Pass 加进 RDG 图。

一句话：SceneViewExtension 决定”在哪插” → AddVignettePass 决定”插什么” → Vignette.usf 决定”怎么算”。

Vignette后处理问题

Build.cs中的PCHUsage = PCHUsageMode.UseExplicitOrSharedPCHs;

在 Unreal Engine 的 C++ 模块构建配置文件（.Build.cs）中，PCHUsage = PCHUsageMode.UseExplicitOrSharedPCHs; 是用来**控制该模块如何生成和使用预编译头文件（Precompiled Header, 简称 PCH）**的设置。

它的核心作用是提供灵活性：优先使用你自定义的显式 PCH，如果没有自定义，就自动使用引擎的共享 PCH 机制来加速编译。

下面详细拆解一下：

1. 先理解什么是 PCH

PCH（预编译头）是把一些庞大且不常改动的头文件（比如 CoreMinimal.h、引擎核心头文件等）提前编译成二进制格式。后续每个 .cpp 文件编译时直接复用这个结果，而不需要重新解析这些头文件，从而大幅缩短编译时间。

2. UseExplicitOrSharedPCHs 的具体行为

这个模式是”二选一”的逻辑：

情况 行为
你在 Build.cs 中指定了 PrivatePCHHeaderFile ✅ 使用显式 PCH（Explicit PCH）。UBT 会用你指定的那个 .h 文件作为该模块所有 .cpp 的统一预编译头。
你没有指定 PrivatePCHHeaderFile ✅ 自动回退到共享 PCH（Shared PCH）。UBT 会分析模块的源文件，把被多个 .cpp 共同包含的头文件提取出来自动生成一个 PCH；或者复用依赖模块（如引擎模块）已经生成好的共享 PCH。

3. 代码示例

4. 与其他 PCH 模式的对比

模式 行为 适用场景
NoPCHs 完全禁用 PCH 排查头文件依赖问题 / CI 纯净编译
UseExplicitPCHs 强制使用显式 PCH，不指定会报错 对编译控制要求极高的底层模块
UseSharedPCHs 强制只用共享 PCH，忽略显式设置 纯依赖引擎的上层模块
UseExplicitOrSharedPCHs 显式优先，无则共享（最灵活） 大多数游戏模块和插件的默认推荐 ✅

5. 优缺点与注意事项

✅ 优点

  • 编译速度快：共享 PCH 能复用引擎已编译好的成果，避免重复工作。
  • 配置简单：游戏逻辑模块通常不需要手动管 PCH，开箱即用。
  • 可精细控制：当你需要把某些第三方库或频繁使用的自定义头文件塞进 PCH 时，随时可以通过 PrivatePCHHeaderFile 切换到显式模式。

⚠️ 注意事项

  • 隐式包含陷阱：因为 PCH 里的内容会自动注入到每个 .cpp，有时你忘了写 #include "SomeClass.h" 但编译照样过（因为 PCH 里间接包含了它）。一旦关闭 PCH 或换环境，就会报一堆找不到符号的错误。建议：代码里始终显式 #include 你直接使用的头文件，不要把 PCH 当万能药。
  • 修改 PCH 内容会导致全量重编：如果你用了显式 PCH 且经常改动 PCH 里的文件，编译加速效果会大打折扣。

总结一句话

UseExplicitOrSharedPCHs 是 UE 推荐的”智能 PCH 策略“——你有显式需求就用你的，没有就帮你自动用共享的，兼顾了编译速度和开发灵活性。

为什么选择AfterDOF加入Pass

在 UE 后处理管线里把自定义 Pass 挂到 AfterDOF，本质上是想让你的效果叠加在”景深已经完成”的画面之上。结合 UE 后处理管线的实际执行顺序，这个位置有几个非常具体的工程理由。

先看清 AfterDOF 在管线里的位置

UE 后处理的总入口 AddPostProcessingPasses 里，Pass 的大致顺序是 ：

从 EPostProcessingPass 枚举来看，AfterDOF 就是你自定义 Pass 可以订阅的一个挂载点——引擎在 DOF 处理完后、遍历 ViewExtension 时会询问”这个阶段你要不要绑定”，你的回调在这个阶段被触发 。

官方对 MTP_AfterDOF 的定义也很直白：Render after depth of field 。

为什么选 AfterDOF：三个核心原因

1. 画面焦点关系已经确定，你的效果不会被”虚化掉”

景深的作用是基于焦点距离对前后景应用模糊，把观者注意力吸引到对焦物体上 。如果你希望自己加的特效（比如角色身上的能量场、UI 元素、某些需要保持锐利的半透明材质）不受景深影响、始终清晰，那就必须在 DOF 之后渲染。

这也是为什么材质层面 Translucency Pass 的默认值是 AfterDOF——半透明物体（如 UI、光效、毛发）默认就跳过 DOF 计算，保证即使背景虚化得很厉害，这些元素依然锐利 。

💡 反过来，如果你想让自定义效果被景深正确虚化（比如模拟真实摄像机对焦），那应该挂到 BeforeDOF，而不是 AfterDOF。

2. 仍处于 HDR 阶段，后续后处理会统一润色

AfterDOF 虽然跳过了 DOF，但它仍在 Tonemap 之前，意味着：

  • 你拿到的是 HDR 场景色（PostProcessInput0），动态范围完整
  • 你输出的结果还会被后续的 Bloom、LUT 颜色查找、Tonemap 统一处理
  • 也就是说，你加的亮度、颜色偏移，会自然融入整个色彩分级流程，不会出现”色调断层”或”超出 LDR 被截断”的违和感

这对需要光照感、辉光感的效果特别重要——比如自定义的体积光、能量护盾，放在 AfterDOF 能让 Bloom 自然地把高亮部分晕开。

3. 避开了 TAA / 运动模糊的深度不稳定期

材质文档里有一个关键细节：MTP_AfterMotionBlur 会禁用深度测试，因为 TSR 的相机抖动会让深度缓冲不稳定，导致重建后处理闪烁 。

而 AfterDOF 在 TAA 和运动模糊之前，这时候：

  • 深度缓冲仍然是稳定的
  • 你可以放心读取深度、法线等 GBuffer 信息做基于深度的效果
  • 同时又享受了”不被景深模糊”的清晰度

这就是为什么很多依赖深度信息的清晰叠加效果（如描边、区域高亮、伤害反馈）会选 AfterDOF——它处在”深度可用 + 已避开 DOF 模糊”的甜蜜点。

对照其他选项，AfterDOF 的独特定位

挂载点 特点 适合
BeforeDOF 会被景深模糊 需要物理正确虚化的半透明物体
AfterDOF 跳过景深、深度仍可用、仍在 HDR UI/特效/描边等需清晰且依赖深度的效果
AfterMotionBlur 禁用深度测试，Lumen 高质量反射也禁用 高速动态、不依赖深度的半透明
BeforeTonemapping HDR 场景色，TAA 之后 需要修复 TAA/GBuffer lookup 问题的效果
AfterTonemapping LDR 颜色，带宽低性能好 最终调色、水印、屏幕特效

一个容易踩的坑

如果你的效果需要”看起来和场景融为一张照片”，AfterDOF 可能不是最佳选择。社区里就有讨论：在虚拟制片环境中，使用 AfterDOF 的半透明材质会因为不参与景深，看起来”很假” 。

⚠️ 经验法则：要让效果”属于这个世界”→ BeforeDOF；要让效果”浮在这个世界之上”→ AfterDOF。

回到你的场景：如果你正在写一个 SubscribeToPostProcessingPass 的 ViewExtension，把回调挂在 AfterDOF，意味着你的 Shader 会在景深合成之后、Tonemap 之前执行——画面焦点已经定稿，你拿到的是干净的 HDR 图像，输出后还能被 Bloom 和 Tonemap 自然加工。这正是大多数”特效叠加类”后处理想要的理想位置。

你的具体效果是什么？如果是描边/区域高亮类，AfterDOF 基本是标配；如果是要做类似景深二次虚化或焦外成像，那得挪到 BeforeDOF 才行。
