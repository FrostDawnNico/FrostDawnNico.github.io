大气渲染

sky atmosphere

吸收+散射，随距离累积

看到的光 = 保留的光+散射光

太阳：方向光/直射光-光线照射到物体：材质反射/发出的光-消光：一部分光被吸收或散射出视线-物体光穿过空气到相机：距离越远背景光可能越弱

空气把部分太阳光散射进视线，距离越远越少-远景的色差越来越大

相机：最终像素

相机看见两部分

1.原来的光变少，消光

2.沿途有光进入视线

看到的光 = 穿过空气后剩下的物体光 + 沿途散射进来的光

距离增加时，原来物体的光保留得更少，沿途空气贡献也会改变，远景出现对比度下降和偏色

各种散射

rayleigh散射-空气分子对短波长光的散射通常更强-蓝天、天空渐变；低太阳经过更长路径后出现暖色趋势

mie散射：气溶胶等较大粒子产生更集中、更偏前向的散射-朦胧、能见度变化、太阳附近亮晕

吸收：部分光能量在传播中被介质吸收-特定波段减少、改变透过光和天空颜色

多次散射：光在进入相机前经历不止一次散射-改变天空整体能量、并为部分背光和阴影区域补充亮度

QuesColle

rider中右键新建Unreal类GameMode类会出现在Rules下而不是Samples下

UE头文件中#include其他内容为什么不能在”.generated.h”之后的行

简单说：.generated.h 不是普通头文件，它是 UHT（Unreal Header Tool）给你这个文件“盖章”的产物，必须放在所有手写 include 之后，作为反射代码的收尾。放后面再写 #include，UHT 会直接报错，且可能引发一连串诡异的编译错误。

一、它到底生成了什么

编译 UE 项目时，构建流程分两步：

  1. UHT 先跑一遍：扫描你头里的 UCLASS / USTRUCT / UENUM / UPROPERTY / UFUNCTION 宏，生成 Xxx.generated.h 和 Xxx.gen.cpp
  2. C++ 编译器再跑：把你的代码和生成代码一起编译

Xxx.generated.h 里塞的是反射基础设施：
• StaticClass() / StaticStruct() / StaticEnum()

• 构造函数注入、序列化、GC 标记

• 属性偏移、函数注册表

• 基于文件名 + 行号展开出来的宏定义

关键点在最后一条。GENERATED_BODY() 宏本身会展开成类似：
BODY_MACRO_COMBINE(CURRENT_FILE_ID, _, LINE, _GENERATED_BODY)
// 例如：FID_xxx_MyClass_h_26_GENERATED_BODY

而这个 FID_xxx_26_GENERATED_BODY 的具体定义，就写在 .generated.h 里。

二、为什么不能放后面

  1. UHT 硬性约定：它就是靠“最后一个 include”来定位反射边界

UHT 解析头文件时，把 #include “Xxx.generated.h” 当作“这个文件的反射声明到此为止”的标记。后面再出现 #include，它会直接抛：

#include found after .generated.h file -
the .generated.h file should always be the last #include in a header

这不是警告，是阻断性错误。

https://forums.unrealengine.com/t/the-generated-h-file-should-always-be-the-last-include-in-a-header-why-is-that/1904506/3
https://blog.csdn.net/enjoysoledad/article/details/157466681
2. 宏展开顺序会乱

GENERATED_BODY() 依赖 .generated.h 里已经定义好的行号宏。如果它后面又 #include 了别的头，那些头里万一也用到反射宏或依赖当前类的完整定义，就会出现：

• “此声明没有存储类或类型说明符”

• 找不到 StaticClass / 未知标识符

• 红波浪线（IDE 没重新跑 UHT 时的典型现象）

而且一旦你在 .generated.h 前插了一行空行，行号整体偏移，GENERATED_BODY_26 对不上生成文件里的 GENERATED_BODY_25，IDE 立刻炸。
https://community.gamedev.tv/t/include-engine-triggervolume-h-in-header-or-cpp-file/92012/2
3. 生成代码假定“前面的类型都已经可见”

.generated.h 里的内容是基于它之前已经写好的类、结构体、枚举、父类、成员类型生成的。如果把这些依赖放到它后面：

• 生成代码引用了一个还没声明的类型 → 编译失败

• 或者更糟：靠前置声明蒙混过关，但反射元数据不完整，运行时 GC / 序列化 / 蓝图暴露出问题

三、正确写法（机械记忆版）

#pragma once

#include “CoreMinimal.h”
#include “GameFramework/Actor.h”

// 其他所有业务/引擎头：放前面
#include “MyInterface.h”
#include “SomeUtility.h”

// 前置声明能解决的，别 include
class UMyComponent;

// 最后一个 include，永远是这个
#include “MyActor.generated.h”

UCLASS()
class MYPROJECT_API AMyActor : public AActor
{
GENERATED_BODY()
// …
};

规则就三条：

  1. .generated.h 是 #include 区的最后一行
  2. 只放“必须让头文件知道完整定义”的 include，其余用前置声明
  3. 纯实现需要的头（比如 NiagaraSystem.h、StaticMeshComponent.h）挪到 .cpp 里

四、常见踩坑场景

⚠️ 有时候你“感觉必须”在后面 include，其实都能绕开：

  • 只需要指针/引用 → 前置声明 class UFoo;

  • 值类型成员、继承 → 才需要真正 include，那就老老实实放 .generated.h 前面

  • 跨模块类型 → 检查 Build.cs 的 PublicDependencyModuleNames

一句话记牢：.generated.h 是 UHT 给你文件“封口”的那行，封口之后再塞东西，既违反契约，也会让生成代码找不到该有的上下文。
