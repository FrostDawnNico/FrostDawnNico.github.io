1.原来的光变少，消光

2.沿途有光进入视线

各种散射

rayleigh散射-空气分子对短波长光的散射通常更强-蓝天、天空渐变；低太阳经过更长路径后出现暖色趋势

吸收：部分光能量在传播中被介质吸收-特定波段减少、改变透过光和天空颜色

UE头文件中#include其他内容为什么不能在”.generated.h”之后的行

简单说：.generated.h 不是普通头文件，它是 UHT（Unreal Header Tool）给你这个文件“盖章”的产物，必须放在所有手写 include 之后，作为反射代码的收尾。放后面再写 #include，UHT 会直接报错，且可能引发一连串诡异的编译错误。

一、它到底生成了什么

编译 UE 项目时，构建流程分两步：

  1. UHT 先跑一遍：扫描你头里的 UCLASS / USTRUCT / UENUM / UPROPERTY / UFUNCTION 宏，生成 Xxx.generated.h 和 Xxx.gen.cpp
  2. C++ 编译器再跑：把你的代码和生成代码一起编译

Xxx.generated.h 里塞的是反射基础设施：
• StaticClass() / StaticStruct() / StaticEnum()

• 构造函数注入、序列化、GC 标记

• 属性偏移、函数注册表

• 基于文件名 + 行号展开出来的宏定义

关键点在最后一条。GENERATED_BODY() 宏本身会展开成类似：
BODY_MACRO_COMBINE(CURRENT_FILE_ID, _, LINE, _GENERATED_BODY)
// 例如：FID_xxx_MyClass_h_26_GENERATED_BODY

而这个 FID_xxx_26_GENERATED_BODY 的具体定义，就写在 .generated.h 里。

二、为什么不能放后面

  1. UHT 硬性约定：它就是靠“最后一个 include”来定位反射边界

UHT 解析头文件时，把 #include “Xxx.generated.h” 当作“这个文件的反射声明到此为止”的标记。后面再出现 #include，它会直接抛：

#include found after .generated.h file -
the .generated.h file should always be the last #include in a header

这不是警告，是阻断性错误。

https://forums.unrealengine.com/t/the-generated-h-file-should-always-be-the-last-include-in-a-header-why-is-that/1904506/3
https://blog.csdn.net/enjoysoledad/article/details/157466681
2. 宏展开顺序会乱

GENERATED_BODY() 依赖 .generated.h 里已经定义好的行号宏。如果它后面又 #include 了别的头，那些头里万一也用到反射宏或依赖当前类的完整定义，就会出现：

• “此声明没有存储类或类型说明符”

• 找不到 StaticClass / 未知标识符

• 红波浪线（IDE 没重新跑 UHT 时的典型现象）

而且一旦你在 .generated.h 前插了一行空行，行号整体偏移，GENERATED_BODY_26 对不上生成文件里的 GENERATED_BODY_25，IDE 立刻炸。
https://community.gamedev.tv/t/include-engine-triggervolume-h-in-header-or-cpp-file/92012/2
3. 生成代码假定“前面的类型都已经可见”

.generated.h 里的内容是基于它之前已经写好的类、结构体、枚举、父类、成员类型生成的。如果把这些依赖放到它后面：

• 生成代码引用了一个还没声明的类型 → 编译失败

• 或者更糟：靠前置声明蒙混过关，但反射元数据不完整，运行时 GC / 序列化 / 蓝图暴露出问题

三、正确写法（机械记忆版）

#pragma once

#include “CoreMinimal.h”
#include “GameFramework/Actor.h”

// 其他所有业务/引擎头：放前面
#include “MyInterface.h”
#include “SomeUtility.h”

// 前置声明能解决的，别 include
class UMyComponent;

// 最后一个 include，永远是这个
#include “MyActor.generated.h”

UCLASS()
class MYPROJECT_API AMyActor : public AActor
{
GENERATED_BODY()
// …
};

规则就三条：

  1. .generated.h 是 #include 区的最后一行
  2. 只放“必须让头文件知道完整定义”的 include，其余用前置声明
  3. 纯实现需要的头（比如 NiagaraSystem.h、StaticMeshComponent.h）挪到 .cpp 里

四、常见踩坑场景

⚠️ 有时候你“感觉必须”在后面 include，其实都能绕开：

  • 只需要指针/引用 → 前置声明 class UFoo;

  • 值类型成员、继承 → 才需要真正 include，那就老老实实放 .generated.h 前面

  • 跨模块类型 → 检查 Build.cs 的 PublicDependencyModuleNames

一句话记牢：.generated.h 是 UHT 给你文件“封口”的那行，封口之后再塞东西，既违反契约，也会让生成代码找不到该有的上下文。

UFUNCTION(Exec)是什么

UFUNCTION(Exec) 是 Unreal Engine（虚幻引擎） 中一个非常实用的 函数说明符（Specifier）。它的作用是：将 C++ 函数暴露给 UE 的控制台（Console），使其可以通过输入命令直接调用。

简单来说，它就是给你的函数开了一个“控制台后门”，方便你随时在游戏运行时执行特定逻辑（常用于调试、GM 指令、快速测试等）。

  1. 基本用法

声明（.h 文件）

#pragma once

#include “CoreMinimal.h”
#include “GameFramework/PlayerController.h”
#include “MyPlayerController.generated.h”

UCLASS()
class AMyPlayerController : public APlayerController
{
GENERATED_BODY()

// 标记 Exec，使其能在控制台调用
UFUNCTION(Exec)
void FlyToLocation(float X, float Y, float Z);

UFUNCTION(Exec)
void HealPlayer(int32 Amount);

};

实现（.cpp 文件）

#include “MyPlayerController.h”
#include “Kismet/GameplayStatics.h”

void AMyPlayerController::FlyToLocation(float X, float Y, float Z)
{
if (GetPawn())
{
GetPawn()->SetActorLocation(FVector(X, Y, Z));
UE_LOG(LogTemp, Warning, TEXT(“飞到了: %f, %f, %f”), X, Y, Z);
}
}

void AMyPlayerController::HealPlayer(int32 Amount)
{
// 假设你的角色有受伤害/回血逻辑
UE_LOG(LogTemp, Warning, TEXT(“回血: %d”), Amount);
}

在控制台中调用

在编辑器或打包游戏的窗口中，按 ~ 键（波浪号） 打开控制台，直接输入：

FlyToLocation 1000 2000 300
HealPlayer 50

函数就会立刻执行，参数之间用空格隔开。

  1. 核心机制：Exec 函数的查找链（非常重要！）

并不是随便在哪个类里写 UFUNCTION(Exec) 都能被控制台找到。UE 有一套严格的查找顺序（查找链）：

  1. PlayerController（最优先）
  2. Controlled Pawn（PlayerController 当前控制的 Pawn）
  3. CheatManager（如果设置了）
  4. GameMode（仅限在服务器/PIE 中）

⚠️ 常见坑点：
如果你把 Exec 函数写在一个普通的 AActor 或 UActorComponent 里，默认是调不到的，因为控制台不知道去那里找。
• 解决办法 1：把函数写在 APlayerController 或 APawn 里。

• 解决办法 2：通过 PlayerController 转发调用。

• 解决办法 3：使用 CheatManager（见下文）。

  1. 参数与返回值限制

• 参数类型：支持绝大多数基础类型和 UE 常用类型，如 int32, float, bool, FString, FVector, FName 等。

• 返回值：Exec 函数通常声明为 void。控制台命令不直接处理返回值，如果你想看结果，用 UE_LOG 打印到屏幕或输出日志。

• 参数数量：可以有 0 到多个参数，控制台输入时用空格分隔。

  1. 网络与权限（多人游戏/防作弊）

Exec 函数默认是在调用者本地客户端执行的。
• 如果你在多人游戏中希望 Exec 命令在服务器端执行（比如 GM 刷道具），你需要：

1. 在 Exec 函数内部调用一个 Server RPC（可靠服务器远程调用）。
2. 或者在 GameMode 里写 Exec 函数（GameMode 只存在于服务器）。

• 权限检查：正式项目中，一定要检查调用者是否有权限（比如 HasAuthority() 或判断是否是管理员），否则玩家随便开个控制台就能输入命令作弊。

  1. 进阶：配合 CheatManager 使用

UE 提供了一个专门管理调试/作弊命令的类：UCheatManager。
你可以继承它，把大量的 Exec 函数写在 CheatManager 里，然后在 PlayerController 中指定：
// 在 PlayerController 里
PlayerController->CheatManagerClass = UMyCheatManager::StaticClass();

这样既能保持代码整洁，又能让所有命令都通过控制台调用。

总结

UFUNCTION(Exec) 是 UE 开发者调试和测试的神器。如果你正在写 SetupInputComponent 处理玩家输入，同时需要一些快速测试角色状态、传送、刷物品的功能，Exec 函数是最快的实现方式——不需要绑定任何按键，打开控制台敲一行命令就搞定。

IE_Pressed是什么KeyEvent，还有哪些常用的keyevent

IE_Pressed 是 UE 传统输入系统里的按键事件枚举 EInputEvent 的一个值，意思是“按键按下的那一瞬间触发一次”，不是按住持续触发。

一、IE_Pressed 到底是什么

// 传统输入系统里的写法
PlayerInputComponent->BindAction(
“Jump”, // Action Mapping 名字（在项目设置里配）
IE_Pressed, // 按键事件类型
this, // 回调对象
&AMyChar::StartJump // 触发的函数
);

• IE_Pressed：手指/鼠标刚按下去的那一帧调用一次

• 适合“开火”“跳跃起跳”“交互”这种单次触发的逻辑

二、EInputEvent 全部枚举值

定义在 Engine/EngineBaseTypes.h：
enum EInputEvent
{
IE_Pressed = 0, // 按下瞬间
IE_Released = 1, // 松开瞬间
IE_Repeat = 2, // 按住时每帧重复触发
IE_DoubleClick = 3, // 双击
IE_Axis = 4, // 轴输入激活（内部用，BindAxis 相关）
IE_MAX = 5 // 枚举边界，别用
};

常用几个的含义

枚举 触发时机 典型用途

IE_Pressed 按下瞬间（一次） 开火、跳跃、交互、切换武器

IE_Released 松开瞬间（一次） 停跳、蓄力结束、松手射击

IE_Repeat 按住时每帧都触发 连续开火、按住加速、持续旋转

IE_DoubleClick 双击时 鼠标双击拾取、锁定目标

三、经典搭配：Pressed + Released 成对写

void AMyChar::SetupPlayerInputComponent(UInputComponent* PC)
{
Super::SetupPlayerInputComponent(PC);

// 跳跃：按下起跳，松开停止
PC->BindAction("Jump", IE_Pressed,  this, &AMyChar::OnJumpStart);
PC->BindAction("Jump", IE_Released, this, &AMyChar::OnJumpEnd);

// 开火：点一下打一发
PC->BindAction("Fire", IE_Pressed, this, &AMyChar::OnFire);

// 持续技能：按住一直放
PC->BindAction("Charge", IE_Repeat, this, &AMyChar::OnCharging);

}

⚠️ 注意：BindAction 是“动作型”输入（离散事件），BindAxis 是“轴型”输入（连续数值，比如移动、视角），轴映射不用 IE_Pressed 这套枚举，它每帧都跑，带一个 float 值。

四、容易混淆的点

  1. IE_Repeat ≠ 自己写计时器

按住一个键，系统默认会按系统按键重复频率不断发 IE_Repeat。如果你想做“每 0.2 秒开一发”，要么用 IE_Repeat 自己在函数里计时，要么用增强输入的 Hold 触发器。

  1. 触屏也能用同一套

PlayerInputComponent->BindTouch(IE_Pressed, this, &AMyChar::TouchStart);
PlayerInputComponent->BindTouch(IE_Released, this, &AMyChar::TouchEnd);

BindTouch 同样吃 EInputEvent。

  1. 增强输入（Enhanced Input）里的对应概念

如果你用的是 UE5 新版 Enhanced Input 系统，旧枚举被换成了 Trigger 类型：

旧系统 EInputEvent 增强输入 Trigger

IE_Pressed Started / Triggered（首帧）

IE_Released Completed

IE_Repeat Triggered（持续）

IE_DoubleClick Combo / 自定义 Trigger

老项目里看到 IE_Pressed 很正常，新项目推荐迁移到 Enhanced Input。

五、一句话总结

• IE_Pressed = 按下瞬间触发一次

• 同族常用兄弟：IE_Released（松开）、IE_Repeat（按住连发）、IE_DoubleClick（双击）

• 它属于 EInputEvent，只用在 BindAction / BindKey / BindTouch 里

• 连续移动/视角用 BindAxis，别用这套枚举

APawn和APlayerController有什么区别

这是 UE 里最基础也最容易混淆的一组关系。理解了它，你对 UE 的整个架构就通了一半。

一句话区分

APawn = 身体（能被控制的对象）

APlayerController = 大脑（发出指令的控制器）

一个玩家 = 一个 Controller（大脑）+ 一个 Pawn（身体）。大脑可以换身体，身体也可以被不同的人控制。

一、本质定位

APawn APlayerController

是什么 世界中的一个实体，能被”占有” 玩家和游戏世界之间的”中介”

类比 身体 / 木偶 大脑 / 提线木偶的人

存在于世界 ✅ 有 Transform、有位置、能被看到 ❌ 没有物理位置，是”隐形”的逻辑对象

数量关系 一个 Controller 同一时刻只能控制一个 Pawn 一个 Pawn 同一时刻只能被一个 Controller 控制

网络角色 每个客户端都有一份拷贝（复制） 只在拥有它的客户端和服务器上存在

二、各自管什么？

APawn 负责的事（身体的事）

✅ 物理表现：Mesh、碰撞体、在世界中的位置和旋转
✅ 移动能力：CharacterMovementComponent 挂在 Pawn 上
✅ 被看到：渲染、动画、粒子
✅ 被碰撞：被子弹打到的是 Pawn
✅ 被拥有：被 Controller Possess / Unpossess

APlayerController 负责的事（大脑的事）

✅ 接收输入：键盘、鼠标、手柄（SetupInputComponent 在这里）
✅ 相机管理：PlayerCameraManager，控制视角
✅ HUD / UI：HUDClass、UMG Widget 的显示控制
✅ 网络同步：客户端和服务器之间的 RPC 通道
✅ 游戏逻辑：菜单开关、暂停、作弊命令（Exec）
✅ 控制切换：Possess 不同的 Pawn（换角色、载具）

三、生命周期：它们怎么配合

游戏启动
↓
GameMode 生成 PlayerController（Spawn PlayerController）
↓
PlayerController 请求生成 Pawn（Spawn Default Pawn）
↓
PlayerController 调用 Possess(Pawn) ← 大脑接管身体
↓
玩家按 W → Controller 收到输入 → Controller 告诉 Pawn 往前走 → Pawn 移动

关键 API

// Controller 控制 Pawn
PlayerController->Possess(MyPawn); // 接管
PlayerController->UnPossess(); // 放手

// Pawn 查询自己的 Controller
APlayerController* PC = GetController();

四、用你的 AtmosphereLab 项目举例

你之前的代码：
// GameMode 里
DefaultPawnClass = AAtmosphereLabCharacter::StaticClass(); // 身体
PlayerControllerClass = AAtmosphereLabPlayerController::StaticClass(); // 大脑

// PlayerController 里
void AAtmosphereLabPlayerController::SetupInputComponent()
{
Super::SetupInputComponent();
InputComponent->BindKey(EKeys::One, IE_Pressed, this, &AAtmosphereLabPlayerController::MainCamera);
// ↑ 大脑接收按键 → 大脑决定切哪个相机
}

这里的设计思路是：
• 按 1/2/3/4 切相机 → 这是”决策”，放 Controller 里 ✅

• 角色移动、跳跃 → 这是”身体动作”，放 Pawn/Character 里

• 天空光照、曝光参数调节 → 这是全局效果，放 Controller 里管也合理 ✅

五、为什么要有这个分离？（设计意图）

  1. 换身体（载具系统）

// 玩家走到车旁边，按 F 上车
PlayerController->UnPossess();
PlayerController->Possess(CarPawn); // 大脑换了个身体，输入和相机自动跟着走

如果输入和移动都绑在 Pawn 上，换身体就得把所有逻辑搬过去，极其痛苦。

  1. 旁观者模式 / 死亡后不销毁

// 角色死了
Pawn->Destroy(); // 身体没了
// 但 Controller 还在 → 可以显示死亡UI、观战、选重生点
// 重生时 → Spawn 新 Pawn → Possess 回去

  1. 网络架构

• 服务器 上每个玩家都有一个 PlayerController（权威）

• 客户端 只有”自己的” PlayerController

• Pawn 在所有客户端都有拷贝（复制同步），但 Controller 不复制给其他人

这就是为什么 RPC（远程调用）要通过 Controller 走的原因。

  1. AI 也能控制 Pawn

APlayerController → 控制 Pawn（人类玩家）
AAIController → 控制 Pawn（AI 敌人）

Pawn 不关心谁在控制它，只管执行移动指令。同一套移动逻辑，人类和 AI 都能用。

六、SetupInputComponent 为什么两个类都有？

APawn 版本 APlayerController 版本

签名 SetupPlayerInputComponent(UInputComponent*) SetupInputComponent()

InputComponent 来源 参数传入 成员变量 this->InputComponent

适合绑什么 角色专属操作（移动、跳跃、技能） 全局/相机/UI操作（切视角、暂停、作弊）

谁调用 Controller Possess Pawn 后自动调用 Controller 初始化时自动调用

你的 AtmosphereLab 项目里，相机切换、天空参数调节放在 Controller 的 SetupInputComponent 里，是完全正确的选择——这些是”玩家决策层面的操作”，不属于角色身体本身。

七、什么时候该放哪？

功能 放 Pawn 放 PlayerController

WASD 移动 ✅

跳跃/蹲下 ✅

动画状态 ✅

鼠标控制视角 ✅（或 Pawn 里处理）

切换相机预设 ✅

开关 HUD/菜单 ✅

暂停游戏 ✅

作弊/调试命令 ✅

血量/死亡逻辑 ✅

武器开火 看设计（通常 Pawn/Character） 也可以 Controller

八、一句话总结

Pawn 是”能被操作的东西”，Controller 是”操作它的人”。

输入进来先到 Controller，Controller 决定怎么指挥 Pawn。

身体可以换，大脑一直在。
