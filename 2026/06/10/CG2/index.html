理解图形学相关原理

渲染顺序

渲染Object顺序：

  1. 先渲染所有不透明（Opaque）
  2. 后渲染所有透明（Transparent）
  3. 不透明：从前到后渲染（近→远）
  4. 透明：从后到前渲染（远→近）

为什么要分顺序？

  1. 深度缓冲（Depth Buffer）

Unity 有个深度图，记录屏幕上每个像素最近的物体距离。

● 远处物体被近处物体挡住 → 直接不画，节省性能。

● 这个机制只对不透明物体生效。

  1. 不透明（Opaque）

● 有深度写入 ZWrite On

● 有深度测试 ZTest LEqual

● 规则：谁近画谁，远的直接被遮挡丢弃

● 渲染队列值：Queue = 2000

  1. 透明（Transparent）

● 关闭深度写入 ZWrite Off（关键！）

● 保留深度测试 ZTest LEqual

● 规则：不能遮挡自己，必须按“远→近”混合颜色 ● 渲染队列值：Queue = 3000

Rendering Path

渲染路径：将场景物体渲染到渲染纹理的过程中所使用的步骤和技术。

常见的Rendering Path：

Forward Shading

Deferred Shading

Forward变种

Deferred变种

Forward Shading

是最简单也最广泛支持的一种渲染技术，它的实现思想是遍历场景的所有物体，每个物体调用一次绘制指令，经由渲染管线光栅化后写入渲染纹理上。

优点：
1。实现简单
2。无需 MRT 的支持，硬件支持广泛
3。完美地支持 MSAA抗锯齿。

缺点：
1。 无法支撑大型复杂附带大量光源的场景渲染， 冗余计算多，过绘制严重

for each(object in ObjectsInScene){
    color=0;
    for each(light in LightsInScene){
        color += light.Shade(object);// for all lights, huge cost when the number of lights is huge
    }
    WriteColorRenderTarget(color);
}

Deferred Shading

是一种基于屏幕空间着色的技术，也是最普遍的一种渲染路径（Rendering Path）技术。它的核心思想是将场景的物体绘制分离成两个Pass：几何Pass和光照Pass，目的是将计算量大的光照Pass延后，和物体数量和光照数量解耦，以提升着色效率。在目前的主流渲染器和商业引擎中，有着广泛且充分的支持。

几何通道（Geometry Pass）将场景的物体信息光栅化到多个GBuffer中。这个阶段将场景中所有的不透明物体（Opaque）和Masked物体用无光照（Unlit）的材质执行渲染，然后将物体的几何信息写入到对应的渲染纹理（Render Target）中。

其中物体的几何信息有：
1、位置（Position，也可以是深度，因为只要有深度和屏幕空间的uv就可以重建出位置）。
2、法线（Normal）。
3、材质参数(Diffuse Color, Emissive Color, Specular Scale, Specular Power, AO, Roughness, Shading Model, …)。

注意：几何通道阶段不会执行光照计算，从而摒弃了很多冗余的光照计算逻辑，也就是避免了很多本被遮挡的物体光照计算，避免了过绘制（Overdraw）。

void RenderBasePass(){
    SetupBuffer();//设置集合数据缓冲区
    //遍历场景的非半透明物体
    for each(object in ObjectsInScene){
        SetUnlitMaterial(Object); //设置无光照的材质
        DrawObjectToBuffer(Object);//渲染几何信息到GBuffer，通常在GPU光栅化中完成
    }
}

光照通道（Lighting Pass）利用GBuffer的几何信息计算每个像素的光照结果，它的核心逻辑是遍历渲染分辨率数量相同的像素，根据每个像素的UV坐标从GBuffer采样获取该像素的几何信息，从而执行光照计算。

void RenderLightingPass(){
    BindGBuffer(); // 绑定几何数据缓冲区
    SetupRenderTarget(); // 设置渲染纹理
    // 遍历RT所有像素
    for each(pixel in RenderTargetPixels){
        // 获取GBuffer数据
        pixelData = GetPixelDataFromGBuffer(pixel.uv);
        // 清空累计颜色            
        color=0;
        // 遍历所有灯光，将光照计算记过累加到颜色中
        for each(light in LightsInScene){
            // 可以采用Gouraud,Lambert,Phong,Blinn-Phong,BRDF,BTDF,BSSRDF等光照模型
            color += CalculateLightColor(light,pixelData);//for all lights
        }
        // 写入颜色到RT
        WriteColorRenderTarget(color);
    }

}

优点：

1.光照计算跟场景物体解构，支持多光源。由于最耗时的光照计算延迟到后处理阶段，所以跟场景的物体数量解耦，只跟Render Targe尺寸相关，复杂度是O(Nlight×WRT×HRT)。延迟渲染在应对复杂的场景和光源数量的场景比较得心应手，往往能得到非常好的性能提升。

2，渲染性能更优，彻底剔除过度绘制（OverDraw）

缺点：

1.如需多一个通道来绘制几何信息，需要多渲染纹理（MRT）的支持

2.更多的CPU和GPU显存占用，更高的带宽要求，有限的材质呈现类型

3.难以使用MSAA等硬件抗锯齿，存在画面较糊的情况等等

4.应对简单场景时，可能反而得不到渲染性能方面的提升

问题1：延迟渲染不支持半透明物体

延迟渲染的核心是 G-Buffer（几何缓冲区），它会将场景的深度、法线、颜色等信息存储在几张纹理中。但 G-Buffer 有一个致命的限制：每个像素只能存储最前面（离摄像机最近）那一个物体的表面信息。

为了解决上述矛盾，现代游戏引擎（如 Unity URP/HDRP、虚幻引擎）通常采用以下标准流程：

● 第一步：渲染不透明物体（延迟渲染阶段）

管线首先正常执行延迟渲染。将所有不透明的物体进行光栅化，把它们的几何信息写入 G-Buffer，并在屏幕空间完成所有不透明物体的光照计算，生成初步的屏幕画面。

● 第二步：渲染半透明物体（前向渲染阶段）

在延迟光照计算全部结束后，管线会将所有标记为半透明（Transparent）的物体单独拎出来。此时，引擎会切换回传统的前向渲染（Forward Rendering）路径。
这些半透明物体会按照从后往前的顺序（Painter’s Algorithm），逐物体进行光栅化和光照计算，并利用 Alpha 混合技术，直接叠加到第一步已经渲染好的屏幕画面上。

问题2：延迟渲染的画面比前向渲染模糊

1.G-Buffer 的数据精度损失

延迟渲染需要将场景的深度、法线、颜色等海量信息存储在 G-Buffer（几何缓冲区）的多张纹理中。为了节省巨大的显存和带宽开销，这些纹理往往会进行数据压缩（例如将高精度的法线信息压缩到较低的位深中）。
这种压缩会导致微小的几何细节和高频的法线变化丢失。当光照计算基于这些“打了折扣”的数据进行时，物体表面的光影细节（比如粗糙表面的微小凹凸感）就会变得不如前向渲染那样丰富和锐利，进一步加剧了整体画面的“柔化”感。

2.由于放弃了 MSAA，延迟渲染普遍采用 TAA（时间抗锯齿）作为主流方案。TAA 的原理是将当前帧与过去几帧的画面进行混合和重投影。这种“多帧混合”虽然能极好地消除锯齿和画面闪烁，但本质上是一种对历史画面的模糊与平均。尤其是在物体快速运动或摄像机转动时，TAA 极易产生运动模糊和拖影（鬼影），导致画面看起来不够锐利。即使是 FXAA 这种快速后处理抗锯齿，也是通过识别边缘并进行模糊涂抹来实现的，同样会牺牲细节。

问题3：延迟渲染不支持MSAA的原因

延迟渲染并非绝对不支持 MSAA（多重采样抗锯齿），但在实际工程应用中，它与传统 MSAA 存在着天然的“八字不合”。如果强行结合，会带来极高的性能代价和复杂的算法兼容性问题。

  1. 显存占用与带宽的爆炸式增长

延迟渲染的核心在于 G-Buffer（几何缓冲区），它需要将场景的深度、法线、反照率（颜色）、材质属性等信息分别存储在多张渲染目标（RT）纹理中。

● 内存翻倍： 如果对 G-Buffer 开启 4倍 MSAA，意味着每一张纹理的显存占用都会变为原来的 4 倍。以 2K 分辨率为例，单张 G-Buffer 可能占用 64MB，开启 4x MSAA 后会飙升至 256MB。如果 G-Buffer 包含 3-4 张贴图，总显存占用将轻松突破 700MB 甚至更高。

● 带宽压力： 这种多倍的内存增长会带来巨大的显存带宽消耗，导致渲染效率急剧下降，这在现代高分辨率游戏中是极不划算的。

  1. 光照计算与几何信息的缺失

MSAA 的核心原理是在一个像素内对多个子样本（Sub-sample）进行采样，以判断边缘的覆盖情况。

● 前向渲染： 在计算光照时，GPU 清楚地知道每个子样本属于哪个三角形，因此可以精确地将光照结果复制到对应的子样本上。

● 延迟渲染： 在光照计算阶段（Lighting Pass），几何信息已经被“拍扁”并存储在了 G-Buffer 中。此时，GPU 只能拿到每个像素的最终属性（如法线、颜色），丢失了原始的几何覆盖信息。GPU 无法判断一个像素内的 4 个子样本中，哪几个属于物体 A，哪几个属于物体 B，因此无法正确地为每个子样本计算并分配光照。

  1. 极其复杂的 Resolve（解析）过程

在常规的 MSAA 流程中，硬件可以自动将多采样的结果合并（Resolve）为最终的单采样图像。但在延迟渲染中，如果对 G-Buffer 开启 MSAA，开发者必须手动编写极其复杂的 Resolve 逻辑：不仅要解决深度缓冲区的合并，还要处理法线、颜色等多个纹理的合并。这完全放弃了硬件自动 Resolve 的高效性（即 On-Chip MSAA 优势），转而采用代价高昂的“软 Resolve”方案。

前向渲染的变种

Forward+ Rendering

Forward+也被称为Tiled Forward Rendering，为了提升前向渲染光源的数量，它增加了光源剔除阶段，有3个Pass：depth prepass，light culling pass，shading pass。

light culling pass和瓦片的延迟渲染类似，将屏幕划分成若干个Tile，将每个Tile和光源求交，有效的光源写入到Tile的光源列表，以减少shading阶段的光源数量。

Forward+存在由于街头锥体拉长后在几何边界产生误报（False positives，可以通过separating axis theorem (SAT)改善）的情况。

Cluster Forward Rendering

Cluster Forward Rendering和Cluster Deferred Rendering类似，将屏幕空间划分成均等Tile，深度细分成一个个簇，进而更加细粒度地裁剪光源。算法类似，这里就不累述了。

Volume Tiled Forward Rendering

Volume Tiled Forward Rendering在Tiled和Clusterer的前向渲染基础上扩展的一种技术，旨在提升场景的光源支持数量，论文作者认为可以达到400万个光源的场景以30FPS实时渲染。
